## 4. P1：D1 的具体修复

### 4.1 已确认原因

`pipeline/arsia_pipeline/storage_restore.py::inspect_optional()` 只匹配大写 `No such volume`；本机实际错误为：

```text
Error response from daemon: get <精确卷名>: no such volume
```

结果是物理删除已完成，却被判定为 `STORAGE_DOCKER_CHECK`，影响重复对账。

### 4.2 最小实现路径

保留现有 Docker CLI，不为本问题引入另一套 SDK 或 Docker 服务。

1. 抽取纯函数 `classify_inspect_failure(kind, identity, returncode, stderr)` 或等价 helper。
2. 对错误文本做限定的空白整理和大小写归一；仅接受已验证的 daemon “此精确资源不存在”响应形态。资源 kind 和 identity 参与匹配，不能只搜宽泛 `not found`。
3. 对 volume 的 `get <name>: no such volume`、container/object 的明确不存在形态提供用例；兼容当前实际 CLI 输出，不猜测所有平台都同一文本。
4. 非零退出码不自动等于不存在。权限、daemon 不可达、超时、socket 错误、未知文本、混合矛盾错误均保持阻断。
5. 命令成功但 JSON 损坏、空列表、对象类型错误或身份不符，同样是检查失败，不能返回 None。
6. 成功返回的身份核验仍沿用 `own()`。只对目标资源的明确 absence 返回 None；不得修改 label/mount/镜像/pin 检查。

核查本次恢复对账链内有无另一个 `except CalledProcessError: ...不存在` 的旁路；相关调用统一使用正确判断。不要把范围扩展成重写全项目 Docker 封装。

### 4.3 必须验证

- 纯函数负例：大小写、精确卷名、容器 ID、不同资源名、未知文本、权限/连接/超时、坏 JSON。
- 真实新容器/卷删除后，再次 inspect 返回明确不存在。
- 对已 reclaimed 的同一 operation 连续两次 reconcile 成功且无新建资源。
- 运行中、共享卷、替换身份、pin 的原拒绝行为仍成立。

## 5. P2：D2 的具体修复

### 5.1 根因与目标

`TestSpace.peak()` 使用 `try/finally release()`；SIGKILL 不执行 finally。当前 reservations 只有 id、bytes、reason，不能可靠关联至恢复 operation。上轮两次 kill 留下合计 1 GiB **预算预留**。

目标是可恢复的预留生命周期，不是定时删除“旧行”。峰值预留与长期保留资源占用必须分开：操作已结束可释放额外峰值，但诊断卷仍需计入持有资源。

### 5.2 持久身份与追加结构

通过版本化追加迁移扩展宿主 catalog，不改写旧初始化正文来冒充迁移；新建和从既有 schema 升级均测试。最小记录：

- reservation_id、space_id、operation_id、operation_kind（create/backup/restore）；
- owner instance/session（创建前尚无 session 时使用持久 creation intent）；
- amount_bytes、reason、状态、created_at/updated_at；
- 操作记录位置/标识、预期资源身份和归属；
- 本次执行的 owner token、可核验执行权/锁；必要的 claim generation；
- released_at、release_reason、reconciliation evidence。

建议状态：`reserved -> active -> released`；不确定转 `blocked` 并继续保守计入。保留释放审计，不仅 DELETE 后让历史消失。金额统计仅累计当前有效预留，幂等释放不能重复扣减。

旧记录缺少操作身份时标记 legacy/unresolved，不凭 reason、时间或“数量刚好两条”猜归属。上轮原 catalog 不在本轮迁移/清空范围；可以复制结构化样本到新测试空间验证兼容。

### 5.3 所有预留调用点都要接入

目前至少有三处：

| 调用点 | 需要绑定的意图 |
|---|---|
| `TestSession.create()` 里的创建峰值 | 在 Docker 资源创建前持久化的 creation intent，包含目标受限路径和 prospective instance/资源身份 |
| `TestSession.archive_database()` | 当前 session 的冷备 operation/归档身份 |
| `RestoreOperation.start()` | 本次 restore operation，而不是无来源的随机 reservation token |

只修 restore 而让 create/backup 仍产生不可归属预留，不算完成 D2 的通用修复。

restore 的 operation ID 应在 reserve 之前生成，先有持久 intent，再关联预留，之后才创建资源。跨两个 SQLite/文件记录不能假装有一个事务：规定可重入顺序，并逐窗口验证“有 intent 无预留 / 有预留未开始 / 已开始未记回执 / 已结束未释放”。

create 可先在 space catalog 中保存受限 creation intent，不必为预算拒绝提前创建目标数据库目录；继续保证超预算不会产生 Docker/重资源。复制 config、分配 ID、登记资源须有清晰顺序。

### 5.4 执行权和安全释放条件

给操作使用精确的执行权/锁，复用既有宿主锁与短 catalog 事务。不要仅凭 TTL 到期或 PID 不存在释放，也不能在新进程可能正在恢复时抢走其预算。

建议对账流程：

1. 在短 catalog 事务领取一个预留的对账 claim，提交后再进行 Docker/文件检查；不长时间持有 catalog 全局写锁。
2. 校验 space/session/operation，取得非阻塞操作锁。获取失败视为仍在使用。
3. 检查精确已登记的 child/helper/container，不运行名称前缀扫描。持锁进程死亡不意味着其 Docker helper 已停止。
4. 完成已有操作对账：确认成功、已取消，或进入明确的 stopped/blocked diagnostic 状态；不自动恢复数据导入。
5. 对仍保留的数据库卷/归档/诊断文件，先保证它们被持有资源记账覆盖。不能靠释放峰值把保留卷记成零。
6. 用同一 claim/generation 和原状态进行条件更新，将峰值预留标 released，写入理由和证据。重复运行结果相同。
7. 身份不清、Docker 检查失败、操作仍在进行、保留资源未登记或新 owner 已接管时，保留预留并返回具体阻塞。

锁序在实现前列出并核查；不能一处持 catalog 等 session，另一处持 session 等 catalog。长操作用 session/operation 锁，catalog 只做短提交。恢复需要新的工作峰值时显式重新申请，不能把旧已释放额度当作仍有效。

### 5.5 对账入口与测试

复用受限 storage CLI 提供 reservations status/plan/reconcile 或等价命令。status 只读；新受管测试生命周期的安全启动/结束点可以调用有界对账，无新 cron/heartbeat。

一次对账最多处理固定数量和时间（沿用现有 100 项/10 秒风格），有剩余返回 pending，不能后台无限循环。只操作新登记的 space。

真实 SIGKILL 至少覆盖：预留后资源前、恢复卷创建后、恢复容器创建后、验证成功后、容器删除后。新进程对账连续两次：无活动峰值泄漏、诊断资源仍保留且计费、无重复删除。create/backup 的同类未完成窗口至少有针对性回归和代表真实边界，未覆盖处如实列出。

### 8.2 G1 通过标准

1. 从上传文件识别真实来源、表粒度、关联关系和可用指标，引用证据可追溯。
2. Agent 自行构建 adapter/合同，样本、全量、独立 QA 均通过。
3. 注册、发布、新 release 查询成功；旧 baseline 来源的记录和查询不变。
4. 私有 oracle 独立核对原始成员、主键、日期、严重程度、已定义的人数指标、关联基数及坐标转换。未知值保持未知，不以0填补资料缺口。
5. 原名和改名同字节重传返回 no_change，batch/release 不变；不得跳过必要 QA。可命中刚刚由 G1 真实建立的 recipe，记录模型是否复用为0。

不能因为图表有数就认定业务正确。独立 oracle 可复用 `verify_autonomous_sources.py` 的只读比对框架，但来源语义预期必须来自官方资料和原始行，不能仅使用 Agent 自己生成的 contract 当答案。

### 8.3 G2 通过标准（实际材料具备时）

先完成 V1，再在同一隔离实例上传 V2：

- 明确新增/修改/删除/覆盖日期变化，不能仅凭文件名、列集合或行数认定同版本。
- 已有 recipe 只是候选；证据和依赖、样本/全量 QA、注册/发布重新检查。
- 结构/含义变化不兼容时，正确转交 Agent 调查，不硬套 V1 的字段与坐标解释。
- 有实质变化按既有发布语义生成新 release；相同规范化内容按既有内容身份规则处理。不得一律期望 no_change。
- 原 release 可查询，当前 release 指向正确版本；重传 V2 返回 no_change。
- V1 重传不使当前数据无意回滚，按既有防回滚政策拒绝或保留当前版本，报告实际结果。

第一版同来源新版本复用已有明确格式/证据限制，执行前核实 `adaptation_v1` 等开关。只能在本轮新配置显式启用并记录；旧 session、正常 runtime 保持不变。未支持的格式应明确退出自动复用并走已有 Agent 路径，不能为通过而增加来源特判。

### 8.4 合理拒绝也是证据，但不是成功导入

可以加一个不调用模型的最小负例：篡改来源绑定、缺少必要主键或构造重复关联键，验证没有发布和没有更改 baseline。改变上传字节的人工结构变体，若缺官方表示绑定，允许被拒绝；不能为了“兼容列重排”放松来源证据。

将结果归为：成功接入、资料不足需要输入、真实数据质量阻断、系统能力缺失、环境/模型传输失败、预算/无进展停止。后五类不能冒充完整泛化通过；但准确停止比发布错误数据更符合目标。

### 8.5 如果 G1/G2 失败

不在同一份留出数据上边改通用代码边反复宣称新来源验收。保存第一次结果，明确它已经变成开发样本。

本轮可以做只读定位和最小复现；生产业务框架修复放入下一轮，届时必须再选新的留出版本/来源验证。若只是本轮工具错误，允许按第 11 节修一次，记录污染边界，不能给运行 Agent 答案或 oracle。

## 9. 额外推进：人工上传材料包（有余量再做）

G1 成功后准备 `manual-test-kit/`，包含原始数据、必要官方资料/下载索引、文件 SHA、步骤说明及上次结果摘要。运行时输入与开发方 oracle 分目录，不把预期映射或答案混进上传包。

准备一个全新、尚未导入 G1 数据的隔离配置/启动入口供用户亲测，或提供可重复创建入口。不能把已经导入成功的数据库当空白环境给用户，导致用户第一次上传只触发 no_change。

不为了交付而让 worker 常驻。可在剩余时间内对现有 `/imports/test` 做一次限定浏览器绑定验证：先保存旧测试绑定，验证正常网站数据源未改变，结束恢复原字节并停止自有 API/worker。若涉及尚未授权的常驻环境启动，只交付启动说明，等待用户实际开始测试。

不要新开替代网站端口、不重启正常3100服务、不修改正常 Imports 默认绑定。复用 `browser_acceptance_binding.py` 前核实其精确归属和恢复条件；绑定被其他操作者改动时不得覆盖。

## 10. 分阶段验收与结论等级

| 阶段 | 内容 | 是否使用数据模型 | 完成后可声称什么 |
|---|---|---|---|
| P0 | 保护、工具/材料/环境预检 | 否 | 实验具备隔离条件 |
| P1/P2 | D1/D2 实现及定向回归 | 否 | 两个通用存储缺陷已修到待真实验证 |
| P3 | R01–R08 有界可靠性验收 | 否 | 被测范围内的恢复/预算/并发可靠性 |
| P4 | 官方材料取得、分类、oracle与输入边界冻结 | 否 | 数据是否具备可执行的泛化测试条件 |
| P5 G1 | 新来源自主导入及重复上传 | 是，按实际需求 | 对这个独立来源的冷启动业务接入能力 |
| P5 G2 | 官方新版本差异、更新及回滚保护 | 是，按实际需求 | 对这个实际版本变化的适配能力 |
| P6 | 人工测试材料和启动入口/可选浏览器验证 | 不另起调查 | 用户可按说明进行下一轮隔离上传 |

不要用 G1 一次成功宣称“任意澳洲数据都支持”。最终报告分别给出：通用机制的覆盖范围、来源/格式/操作限制、Agent 真实介入、开发方参与以及尚未验证的组合。

## 11. 时间与修正约束

整轮最多 **180 分钟**，这不是要求用满。建议预算：P0 15分钟；D1/D2开发和回归60分钟；真实可靠性窗口25分钟；材料预检15分钟；G1/G2各20分钟；报告及可选交付25分钟。前面超时会挤占后续阶段，不能重置总时钟。

- P3 开始前冻结生产代码；P3 窗口最多一次与 D1/D2 直接相关的最小修正，修后重跑受影响关卡且沿用原截止时间。
- P3 安全门槛未通过，停止后续模型实验，保存部分交付。
- G1/G2 各一次新尝试；同一个 job 内 Agent 的受限 adapter 修订允许，按现有预算/无进展机制停止。开发方不得额外反复重开 job。
- 正式自主阶段只允许一次轻量工具修正且不涉及给 Agent 答案；生产业务规则变化则本轮该留出结论失效，保留原失败并暂停。
- 同时一个重型导入/备份/恢复；平时最多两个新测试数据库运行。只为并发验收创建必要小型 child，不运行一堆平行真实模型导入。
- 无周期任务、无自动续跑；剩余时间不足以完成一次重任务和安全收尾时不启动它。
- 到限后先停止新增、使用现有取消机制、确认自有 worker/模型调用/容器状态，再保存报告。不得删除诊断来赶时间。

本轮选择两项真实泛化测试是目标，不保证数据取得或 Agent 处理必然成功。未完成时报告具体阻塞，不再扩展到更多州碰运气。
