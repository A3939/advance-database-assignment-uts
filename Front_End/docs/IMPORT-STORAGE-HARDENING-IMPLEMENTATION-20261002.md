## 5. 问题一：恢复验证副本自动回收

### 5.1 区分“验证”与“留作使用的恢复”

明确区分两种调用目的：

- `verify_only`：自动化归档完整性/业务查询验证。成功且证据持久化后，默认回收本次新建副本。
- `restore_for_use`：操作者需要继续检查或使用恢复数据。默认保留，记录 keep/pin 原因。

不要无条件改变 `restore_database()` 默认行为导致既有人工恢复结果消失。所有自动验收调用点显式选择验证模式，人工模式兼容；参数具体命名可按现有风格调整。

### 5.2 持久恢复操作与状态

在创建任何 Docker 资源前，将恢复操作注册到既有宿主台账/journal，至少记录：operation_id、父 instance/session、用途、源归档身份与 SHA、镜像 ID、目标卷精确名称及创建凭证、目标容器 ID（创建后补齐）、挂载、验证结果、保留策略。

建议状态：

`intent -> restoring -> verified -> cleanup_pending -> reclaimed`

失败或不确定转为 `blocked/retained` 并保存原因；需要继续使用的成功恢复转为 `verified_retained`。字段名可调整，但必须能区分数据验证结果与资源清理结果。

标签同时绑定父 instance、父 session 和 restore operation；不要仅用一个随机 session label 表示全部归属。容器和卷均应有对应信息，源备份不能成为清理目标。

### 5.3 成功回收条件

必须全部满足：

1. 原归档完整成员校验和 SHA 仍匹配；恢复查询符合预期；
2. 验证 JSON、逐表 count/SHA、关键查询、日志及恢复入口已原子落盘；
3. 没有保留 pin、使用 lease 或未知引用；
4. 本次新容器已正常停止，ID、镜像、所有权、挂载与记录一致；
5. 数据卷只被该副本引用；移除容器后再次确认无其他引用；
6. 写入 `cleanup_pending` 后按精确身份回收，再写入 `reclaimed`。

不使用 `rm -f` 代替协调停止。归档损坏、恢复不一致或清理失败不能抹掉诊断；已通过的数据验证也不能被重新标记成导入失败。清理失败应单独报告，可再次执行同一维护操作。

### 5.4 恢复时的边界

覆盖创建卷后未启动容器、容器已创建但 ID 回执未保存、验证成功后未开始清理、容器已删除但卷未删除等窗口。

只有具有完整新版本恢复意图、用途和归属证明的临时资源才可自动对账。验证前中断的非空数据库默认保留诊断；不要自动销毁唯一失败现场。检查失败时不得把异常吞掉后宣称无残留。

对历史 restore 收据只提供只读说明，不自动采用或删除旧副本。

## 6. 问题二：跨轮次保留与受管空间预算

### 6.1 新增小型测试空间目录索引，不做全盘发现

采用显式 opt-in 的宿主 catalog/registry：独立于单次 session 数据库、位于明确允许的测试空间内。可用现有 SQLite 工具；无需引入服务。

新 session 创建时登记，不根据扫描结果自动收养。目录索引至少记录：space_id、session/instance ID、规范化 session 路径、marker 摘要、suite、生命周期分组、完整兼容性指纹、状态、策略、pin、预算预留及完成时间。

catalog 是发现索引，session marker/journal 和实时 Docker 状态仍是归属依据。损坏/缺失/路径越界/ID 冲突时停止本项维护；不可退回宽泛目录扫描。无 catalog 的旧调用保留原行为，不自动迁移旧实例。

为验证跨轮次，本轮建立一个新 catalog，主动创建至少三个不同 run 子目录下的 session；它们从创建时即属于这个空间。不能依赖回收历史环境来完成验收。

### 6.2 分开“保留分组”与“能否复用实现”

目前 baseline/input_set 精确分组的结果，是每次变化都可能获得新一组最近两个配额。调整为两层：

- **生命周期分组**：由受信任测试配置定义的 space/purpose/suite/retention-policy family；同类实验跨 run 目录可比较保留次序。
- **完整兼容性身份**：输入集合、源码/可信 QA 版本、数据库 schema、镜像、adapter 等。继续完整保存，用于恢复和结果解释，不能因保留分组相同就视为同结果或可复用候选。

同 suite 新源码或新输入的成功环境，允许把较旧展开数据库归档；这只是改变存储形态，不合并结果或丢掉证据。禁止按州名、TAS、固定 SHA 编写特判。

每组最近 N 个成功环境保留展开，N 从策略读取，默认 2，不写死。`keep_full`、pin、活动/needs_input、可恢复任务、唯一失败诊断、共享数据库及无法核实归属的对象优先保护。保护例外超过 N 要如实报告，不能取消保护来满足数量。

失败仍按既有失败指纹保留首个和最近一个必要现场；不要合并输入/错误语义不同的失败。

### 6.3 执行与并发

复用 `archive_database()`：先完成安全关闭和独占检查，完整冷备校验后才移除展开数据库。发布文件、收据、QA 证据、归档及恢复依赖仍保留；本轮不要求搬迁所有发布输出。

catalog 领取维护项使用短事务/claim；执行期间使用现有单 session 锁，完成后更新索引。不要持有 catalog 全局锁做压缩或长时间 Docker 操作，也不要同时长期持有多个 session 锁。过期 claim 仅触发重新核验，不直接授权删除。

两个 finalizer 同时运行不得重复回收或绕过 pin。计划应用时重新核对策略、当前引用和资源身份；新 pin、lease、上传或资源被替换，旧计划必须失效。

### 6.4 预算和增长边界

保留现有每 session 预算，并为显式受管 space 增加聚合预算/新任务预留。最低覆盖：展开文件、暂存、归档、恢复副本、数据库卷以及新备份所需峰值。逻辑字节、宿主分配字节、Docker 报告/预留字节分别展示，不重复计数。

本轮建议新空间预算 8 GiB、宿主可用空间预留至少 2 GiB，可由受信任本地配置调整；测试用小阈值注入验证。预算超限后先尝试合法收尾；仍不足则拒绝新增重测试并解释 protected/archives/unknown 分量，不先删原件腾备份空间。

Docker 无法可靠测量时记录 unknown，并使用明确的保守预留或阻断新增重任务；不能按 0 字节记账后宣称硬上限有效。不承诺 Docker Desktop 虚拟磁盘即时收缩，也不实现容器磁盘硬配额服务。

必须明确：最近 N 个限制的是符合条件的展开成功环境，不是归档总量。归档和必须保留的输出仍会增长；到预算边界应停下等待用户，而不是无限增加或自动永久删除归档。

## 7. 问题三：上传孤儿与硬中断恢复

### 7.1 以真实提交与引用为准

复用 `api.upload()`、`input_store`、`storage_lifecycle.maintenance()`，先画出 SQL/upload reservation、job row/table lock、host ledger lock 的实际获取顺序，再保持一致。不能在 GC 与上传之间引入反向锁序。

`receipt_pending_commit` 没有后续 `receipt_committed` 不等于上传失败：SQL 可能已经提交，只是响应或 journal append 丢失。**已持久化的 jobs.files 和其他业务引用为判定依据**；确认已提交后补齐台账记录，保留输入，不触发重新导入。

引用检查应覆盖上传收据、jobs、batch/release、registry/source/adapter、attempt、agent checkpoint/evidence 和当前 lease。复用现有全量引用保护，不用单个文件引用计数替代它；任何不确定情况保守保留。

### 7.2 暂存意图、状态及宽限期

在 `.part` 创建前写入最小持久上传意图：instance/session/job/upload ID、受限路径、创建时间、owner/lease、状态。blob/staging/receipt/SQL commit 的阶段变化记录到同一可追溯操作中。

补充 orphan candidate 状态，如 `staging -> pending_commit -> committed`，或 `orphan_candidate -> quarantine -> reclaimed`。状态名可调整。不要把所有失败 job 的原始输入列为孤儿。

默认宽限期可取 24 小时并受信任配置化；测试注入时钟验证，不等待一天，也不篡改宿主时间。宽限期是必要条件之一，不是单独删除依据。时钟回拨、缺时间、lease 不明均保留。

对未提交且可证明无任何引用的 receipt/暂存，可采用原子隔离再回收；保留最小 tombstone（身份、原因、原 SHA/大小、动作时间和引用判定摘要）。确实没有任何成功上传或保留对象依赖的 orphan blob 才能删除。

共享 blob 不随一次上传回滚而删除。`needs_input` 和可恢复 checkpoint 的依赖继续保护；对整个实例仍有活动任务时，允许沿用保守延迟策略，不为提高回收数量绕过它。

### 7.3 在可信安全点调用

默认先提供显式、受限 `reconcile`/GC dry-run 与 apply 能力，再接入受管测试启动/结束的安全点。每次运行有数量/时间上限，例如 100 个候选和 10 秒，超出返回剩余数量，后续安全点继续；不后台循环。

维护只在取得必要的 worker、上传、数据库及宿主锁并实时重查后执行。数据库不可用则不根据 journal 猜测没有引用；旧 plan 不能无条件执行。只读 status/页面轮询不能触发清理。

### 7.4 硬中断必须是真实子进程终止

用新建测试子进程 + 精确 barrier/pipe 进行阶段同步，由父测试在指定持久边界向自己的子进程发送 SIGKILL，再用新进程执行对账。禁止用 `raise KeyboardInterrupt`/monkeypatch 异常代替全部硬中断验收。

至少覆盖：

1. `.part` 写入期间（持久 intent 已存在）；
2. blob/receipt 发布后、SQL 尚未提交；
3. SQL 已提交、committed journal 尚未写入；
4. 恢复验证已写入成功证据、删除副本之前；
5. 容器已删除、卷尚未删除。

每次终止都只针对测试记录的自有进程；禁止名称匹配 kill、停止 Docker daemon、模拟整机断电或杀正常网站。数据库连接断开/事务回滚后再证明锁已释放；PID 消失本身不是充分证据。

新增 barrier 必须是可信测试钩子，默认关闭，不能让上传用户指定宿主操作。确认重启不会重复导入、重复发布或误删提交成功的数据。

| P1 | 恢复用途、操作台账、成功回收及重入 | `test_session.py`、`storage_lifecycle.py`、`storage_cli.py` | 身份/损坏/pin 负例通过，验证副本可回收 |
| P2 | 显式跨轮 catalog、保留分组、预算 | 复用 Ledger；必要时新增小型 `storage_catalog.py` | 三个 run 目录可保留最近两组，保护例外和并发安全 |
| P3 | 上传意图、引用对账、孤儿 GC、硬中断 | `input_store.py`、`api.py`、`storage_lifecycle.py` | 提交状态不确定时不误删，无引用孤儿能收敛 |
| P4 | 冻结源码、一批隔离验收、报告和暂停 | 现有 `verify_storage_isolated.py` 及有界故障工具 | 逐项证据、资源收尾、恢复检查点 |

这是建议模块分工，不要求为了满足命名新建模块。已有接口可局部扩展，但不要把 Docker、API、catalog、引用判定全部堆进一个大函数。前端不新增页面；确需返回新增维护状态时，保持契约兼容并做对应检查。

## 9. 验收矩阵

每项状态只能填 `pass / fail / blocked / not_run`，附证据路径、源码哈希、测试类型及限制。必要子项未测不能把整项写成 pass。

| ID | 必须证明的行为 | 验收方式 |
|---|---|---|
| H01 | verify_only 成功后日志/证明保留，副本容器和卷消失，原备份不变 | 真实 Docker 恢复 + 删除后清单 + 哈希 |
| H02 | restore_for_use/keep/pin 不自动删除；失败恢复保留诊断 | 单元负例，至少一个真实失败或保留场景 |
| H03 | 错 marker、卷共享、容器被替换、Docker 检查报错均阻断清理 | 受限负例；明确不存在与服务不可用分开 |
| H04 | 验证后中断、删容器后中断均可幂等恢复收尾 | 真实 SIGKILL 子进程；重跑对账两次无副作用 |
| H05 | 三个不同 run 目录的同 suite 成功环境只保留最新 N 个展开数据库 | 新 catalog + 真实 Docker；至少一组基线/输入身份不同 |
| H06 | N 可配置；未知环境、越界路径、历史目录不进入清理 | 定向回归，N=1/2；索引伪造负例 |
| H07 | pin、needs_input、唯一失败和共享子数据库优先保护；两个 finalizer 不重复删除 | 单元 + 真实 PG 锁/并发代表场景 |
| H08 | space 预算覆盖所有已登记类别、归档峰值；超限拒绝新重任务且保留原件 | 小阈值/unknown 注入；无需填满磁盘 |
| H09 | 过宽限期、无引用的 `.part`/pending receipt/orphan blob 可回收 | 真实 PG 引用检查 + 可控时钟；清理后 tombstone |
| H10 | SQL 已提交但缺 committed journal 的上传修复台账且保留字节 | 真实提交窗口 SIGKILL；随后仍可 resolve/导入 |
| H11 | 未提交崩溃、共享同 SHA 并发、事务回滚均不损坏另一上传 | SIGKILL + 独立成功引用检查；无活动期误删 |
| H12 | DB 不可用、lease/锁占用、宽限期未到、未知 staging、路径符号链接均保留 | 定向负例；不能靠忽略错误达成无残留 |
| H13 | 固定材料首次导入成功，两次重传（原名/改名）均 no_change | 真实 API/worker、样本/全量独立 QA、注册、发布、查询 |
| H14 | 非空已发布数据库冷备/恢复后业务结果一致 | 新建发布库包含 632 条保存的 TAS 记录，恢复后 count/逐行 SHA/current release/代表查询一致 |
| H15 | 维护失败不改导入成功状态，不启动模型或新导入；最终无自有活动进程 | 错误注入 + 模型拒绝桩/日志 + 资源审计 |
| H16 | 原环境、历史归档、旧 pin 及业务身份/QA 语义没有变化 | 保护基线复核；数据库无法比对时单独标 not_verified |

H13/H14 优先复用已有保存的 TAS 输入、已验证 adapter/recipe 和必要的已缓存官方证据，创建全新隔离数据库。使用 fixture 的部分明确标注“固定材料/adapter 回归”，不宣称新的自主识别成功。若本地材料/镜像缺失，标记阻塞，不在线下载或调用模型补齐。

H14 不要求恢复旧验收环境；应归档本轮新创建且已发布的测试库，在新副本验证。业务表非空及 current release/query 是必要条件，不能用空表或只执行 `SELECT 1` 替代。校验期间只读业务数据，原备份保持不变。

存储规则的泛化验收另用两种无州名的合成上传材料和不同内容/文件名/来源标签进行去重与引用负例，验证规则不依赖 TAS。完整多格式 parser 矩阵和新州业务泛化不在本轮结论范围内。

## 10. 时间、资源和停止条件

- 开发、定向测试及报告总墙钟目标上限 **120 分钟**；源码冻结后的隔离集成窗口最多 **30 分钟**，均为本轮执行约束。
- 只安排 **一批预先列明的集成验收**，含 H01–H16 所需场景；不是每做一处修改就再跑一整批。
- 同时最多一个执行中的重型导入/备份/恢复；正常运行的测试数据库最多两个，额外保留环境可以停止。不能在 finalizer 内隐式拉起旧任务。
- 集成发现本范围的小问题，允许最多一次最小修正；新哈希下重跑受影响场景及 H13/H14 关键路径，仍须在原 30 分钟窗口内。否则记录失败，不能拼接旧源码通过记录冒充当前源码全通过。
- 不在时间临近结束时开启新重任务。到限后先停止新增，使用取消/停止机制收尾本轮自有资源，保存检查点，不为了卡时间强删活动数据。
- 发现归属错误、原环境变化、误删风险或业务 QA/发布身份回归，立即停止破坏性维护，保留证据并暂停。源证据既有失败不作为扩展本轮范围的理由。
- 不具备运行条件的项目记录具体阻塞；不得扩大权限、下载新依赖/模型、修主库连接或无限重试。

三个目标可分别完成。任一未满足必要验收条件，应写“部分完成”，说明可用边界和下次最小步骤；不要为得到一个总通过而删除断言、放宽引用保护或排除失败样例。

## 11. 最终交付与暂停检查点

保存到本轮唯一 artifacts 目录：

1. `REPORT.md`：三个目标逐项结论、技术变更、实际收益和未完成项；特别说明仍会增长的归档/必要输出。
2. `VERIFICATION.json`：H01–H16 结果、证据、测试类型、源码/镜像/输入身份；已有业务失败单列。
3. `SOURCE-before.json`、`SOURCE-final.json` 和本轮修改清单：区分开始前已有未提交变化，禁止 reset/stash 覆盖用户工作。
4. `STORAGE-MEASUREMENTS.json`：清理前后逻辑/分配/Docker 报告字节、未知量、归档与证明开销、候选保留原因；不同口径不相加冒充物理释放。
5. 创建、关闭、归档、恢复、回收的 journal、manifest、原始日志与逐表/查询验证。
6. `checkpoint.json`：status=paused、最后阶段、每个自有进程/容器/卷状态、未完成维护操作、pin、恢复命令与停止原因。

报告阶段时间包含开发、定向回归、固定材料导入、QA、备份、恢复、回收和收尾；区别总墙钟与各步骤累计耗时。

成功 disposable 恢复副本应已回收；失败/硬中断证据按 pin 保存；不要删除源归档和唯一失败现场以得到“零残留”。所有保留都有理由，所有已回收都有证据。

本轮数据模型调用预期为 0：用运行审计证据确认；不能仅因配置说禁用就推断为零。主库无法连接则明确“未完成主库内容比对”。

完成后仅报告结果并暂停，等待用户决定真实新数据集和下一阶段任务。不要自行恢复旧目标、启动新测试或给其他线程发送后续开发指令。
