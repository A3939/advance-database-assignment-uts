### 2.3 必须解决的语义陷阱

1. `store.FINAL` 包含 `needs_input`。它表示某种处理阶段结束，**不表示可以清理**。等待用户补充信息的 job、checkpoint、输入和未完成候选必须保护。
2. 发布结果、QA 文件、agent steps 和恢复检查点可能引用 attempts 内的文件。不能按文件夹年龄、任务显示状态或“数据库已有数据”直接删除。
3. API 当前失败路径会 `unlink(final)`。内容去重后 final 如果变成共享 blob，这个动作可能删掉另一成功 job 的输入。失败上传只能清理自己创建的暂存资源或撤销自己的引用。
4. executor 与 `scoped_orphans.inspect_owned` 当前约定两个 bind mount 及严格路径。改变输入提供方式时必须同步验证归属契约；不能删掉挂载校验来让去重通过。
5. 文件名、格式、角色和上传身份不能被 SHA-256 文件名取代。内容相同不等于同一个上传事件，也不等于必然得到相同解析语义。
6. executor 已有 `work_bytes`、`reserve_bytes` 和输出上限。需要统一统计与策略，不要再创建一套相互冲突的限额。
7. `config.py`、测试工具和前端 bridge 各有环境绑定约束。新 CLI/API 必须显式使用经校验的测试实例；不能隐式回退到 `imports-local/runtime.json`。

## 5. 资源台账、引用与锁

### 5.1 最小持久信息

每个资源至少记录：

- resource_id、instance_id、test_session_id，以及适用的 job_id/attempt_id/run_id。
- kind：raw_blob、upload_receipt、execution_input、candidate_output、qa_work_db、evidence、archive、container、database_volume 等。

- 生命周期状态、大小、SHA-256、创建与最后状态变更时间。
- 被谁引用、保留理由、pin、策略版本、归档位置及验证状态。
- Docker 所有权标签/收据摘要、允许的挂载及专用资源证明。

活动实例可使用追加迁移保存结构化台账和 maintenance queue。整个测试数据库自身被归档后，仍须有宿主侧 session manifest/journal 能定位它；不能将唯一恢复索引放在已被移除的数据库里。

### 5.2 清理判定

分别实现并测试“任务处理结束”“可恢复”“资源可归档”“资源可删除”，禁止用单一 `FINAL` 枚举代替全部判断。

候选资源必须同时满足：

1. 属于明确受管的测试实例及清理 session；
2. 没有活动 worker、executor、上传、恢复或维护操作持有使用权；
3. 不被当前/受保留的 release、batch、registry、checkpoint、待答复 job 或 pin 引用；
4. 保留策略允许；
5. 删除前已满足本类资源的证据或备份要求。

第一版保守保留仍有引用的发布输出，不强制移动当前 published canonical 文件。无法证明没有引用时视为有引用。对 DB JSON、agent_steps.evidence_path、保存的 session/checkpoint 等现有引用进行明确梳理，不能只扫描文件名。

第一版不自动淘汰数据库中的历史 release/batch。它们仍被承诺可查询时，其恢复依赖必须保留；若因此超过保留目标，报告 protected 的原因。

### 5.3 同步与恢复

- 复用既有 worker 全局锁/instance marker 规则，明确与上传锁、job row lock、维护锁的获取顺序，避免死锁。
- worker 持有全局 session lock 时，外部维护程序不能直接绕过它。活动实例的变更可由维护队列在 worker 安全点串行执行；只读 API 不直接清理。
- 已结束独立测试环境的回收由拥有该环境的 test session finalizer 执行，先停止其自有 worker/API/executor，再正常关闭专用 PostgreSQL，保留宿主 journal。
- 归档期间必须获得防止源变更/新引用的有效保护。仅“开始检查一次”或“进程看起来没有运行”不足以防竞态。
- 设计 claim、校验、更新引用、删除之间的原子步骤和恢复点。每步可重复执行，崩溃后不能把半成品视为完成。
- 若注册/领取资源与 Docker 创建之间可能被 kill，先写 intent/标记，再创建，重启时仅按此意图核对本轮资源；不要只依赖 finally。

## 6. 默认保留策略

策略有版本，范围限定新受管测试环境；配置从受信任本地配置读取，浏览器不能改写根目录或 Docker 范围。

| 类型 | 默认策略 |
|---|---|
| 唯一原始输入、上传身份与来源证据 | 保留；同环境同字节内容可去重，收据不合并 |
| 运行中/排队/等待输入/恢复中任务 | 完整保护，不自动清理 |
| 被保留 release、registry、checkpoint 引用的内容 | 保留，不受“最近两套”数量覆盖 |
| 成功的完整独立测试环境 | 按可比较的测试套件/基线分组，最近两套保持展开；更旧者在验证归档后回收 |
| 失败环境 | 同失败指纹保留首次和最近一次完整诊断；其余先归档，仍保留每次结果摘要 |
| 无引用且可再生成的执行输入/QA 工作文件 | 必要结果和诊断已落盘后回收 |
| 压缩归档 | 本轮不自动永久删除；纳入预算，接近上限时提示，超限时停止新增重测试 |
| 用户 pin 或归属不明的资源 | 一律不自动清理 |

失败指纹应包含错误类别/阶段、可信实现版本、输入集合、候选/合同相关版本；排除纯时间戳、随机 job ID 等噪声。不能把有相同错误文案的不同数据问题合并丢弃。

总空间预算必须包含展开数据、归档、上传暂存及需要的备份峰值。预留空间不足时不要为了腾出压缩空间先删除原件。明确归档留存并不等于永久零增长，报告配额与人为 pin 带来的保留压力。

不要在本轮引入 cron/heartbeat。收尾由测试生命周期触发，必要恢复在显式启动或维护命令执行；不新建后台定时任务。

## 7. 归档与恢复实现要求

### 7.1 文件归档

可先使用 Python 标准库 tar/gzip 与 SHA-256，不为本轮额外引入存储服务。算法可配置，优先正确性与现有可用依赖。

推荐状态序列：

`retained -> archive_planned -> archiving -> verified -> eviction_pending -> archived`

`blocked` 保存具体原因；`restoring -> restored` 是单独流程。只有 verified 且删除前条件再次成立，才允许回收展开文件。

流程至少包括：

1. 保存受限且版本化的清理计划，列明对象、原因、引用、空间估算与计划有效性条件。
2. 生成 manifest；拒绝符号链接逃逸、设备文件、越界路径等不受支持对象。
3. 写 `.partial`，正确关闭并完成持久化，再原子替换为正式归档。
4. 重新读取压缩包，核对成员完整性、逐文件内容及恢复必要的元数据。
5. 核对源没有变化及引用/所有权条件仍成立，持久化 verified。
6. 回收允许清理的展开副本；保存归档定位与审计记录。已有证据链接应显示“已归档/需恢复”，不能伪装成普通文件不存在。

压缩命令退出码为零、只检查 tar 列表、只保存外层 SHA-256，均不足以代替逐文件验证。

### 7.2 专用测试数据库

- 只处理该测试 session 独占的 PostgreSQL 容器/卷。多个测试数据库共享一个容器时，不得删除整个容器或卷；第一版可明确跳过并报告原因。
- 原容器须正常退出，确认集群关闭状态。冷备包括整个 PGDATA、WAL 和必要配置，保存镜像 digest、版本和 UID/GID。
- 有外部 tablespace、额外挂载、无法解释的容器层更改或未正常关闭时，停止自动清理；不能做不完整冷备后删除。
- 保存 container/volume inspect 和原容器日志，私有配置权限限制为 0600，不经过浏览器 evidence API。
- 归档及校验后才移除精确自有容器和 volume；共享镜像不随环境删除。
- 恢复必须使用新建、唯一标记的环境，默认无网络、无主机端口，禁止覆盖现存目录/卷/数据库。
- 恢复抽验至少验证全部文件哈希、PG 启动、业务表和若干确定查询结果。不能只用 `pg_isready` 宣称数据恢复正确。

### 7.3 最小恢复包

保留原始文件定位/哈希、parser/adapter/contract、来源证据快照、依赖镜像 digest、执行与独立 QA 报告、batch/release、阶段时间与调用计数，以及恢复 manifest。

全量原始内容与大中间表不用重复嵌入每份 JSON 报告。摘要可引用不可变对象，但必须保证引用的对象仍保留或可恢复。

失败、取消、中断亦须有收尾记录。可恢复 checkpoint 的内容不能作为一般临时文件提前清理。

## 8. 内容去重与暂存文件

### 8.1 上传内容存储

去重范围先限定单一隔离 instance，不跨用户、正常网站或其他测试根共享。

推荐采用 content-addressed blob，加每次上传独立 receipt：

- blob 按服务端实际流式计算的 SHA-256 定位，不接受客户端声称的哈希作为信任依据。
- receipt 保留 file_id、job_id、原始名称、格式、字节数、哈希及上传时间。
- 第一次上传安全创建不可变内容；同字节后续上传创建新 receipt/reference，不重复落永久原始文件。
- 并发创建使用原子发布及唯一性约束；不能覆盖现有同名对象。对象存在时核对可信元数据，发现损坏则隔离/阻断，不能继续复用。
- 输入大小、bundle/file 数量与 pending 配额继续按用户提交语义计数；物理去重不能绕过工作量限额。
- 未知 Content-Length 仍受流式大小与临时空间限制。相同文件上传过程中允许有受限暂存副本，结束后不能遗留。

DB 引用与文件落盘之间设计可恢复顺序：失败提交不删共享 blob，创建后未引用的孤儿只能在没有活动 reservation、超过明确宽限且重新核对引用后回收。

本轮不做旧文件自动迁移。已存在的 path-based receipt 保持可读，新 receipt 可以带显式版本。统一 resolver 必须核对其实例边界和哈希；不能扩大成可读任意宿主文件。

检查所有读文件位置是否根据物理路径后缀猜格式。hash 路径无后缀时必须使用被验证的原始格式/receipt 信息；CSV 改名、Excel、ZIP 等不能因去重丢失解析上下文。

### 8.2 沙箱输入

先保持现有只读输入和归属约束。可采用受支持的写时复制或经严格核验的只读输入视图，无法安全共享时使用原有复制回退，并记录回退与实际空间收益。

- 禁止把可写硬链接、普通 chmod 或符号链接当成充分的隔离证明。
- 沙箱不能修改原始 blob、其他 job 输入、宿主 receipt 或策略文件。
- adapter/run.json 仍是每次执行独立的输入上下文。
- 如增加逐文件 mount 或改变路径布局，必须版本化 ownership 契约，同步修改 `scoped_orphans` 正负例；旧收据按旧版本验证，不能通过放宽成“路径大概在 root 下”兼容。
- 不得改变文件角色、规范化顺序、输入哈希、QA 身份和发布身份。
- 执行输入副本在没有恢复用途、证据已保存且执行结束后回收；当前 run 输出供独立 QA/注册/发布使用时不得提前删除。

### 8.3 QA 工作数据库

区分 QA 工作 SQLite 和已签出的 QA JSON/诊断证据。

- 成功时：结果/诊断原子落盘，所有连接关闭，再删除仅供工作使用的 SQLite 及属于它的临时侧文件。
- 失败时：先保存足以解释错误的诊断；按失败保留策略处理，不得无条件 finally 删除唯一失败证据。
- 取消/进程中断时：留下可识别的清理 intent，由拥有此资源的 session 下次收尾；不扫描全盘删除 `*.sqlite`。
- 任何错误都不能修改独立 QA 的原行比较、计数、坐标或语义判定。

## 9. 运维接口与 Imports 展示

### 9.1 受限 CLI

提供等价于下列职责的 CLI，名称可按项目规范调整：

- `inspect/status`：只读资源清单和空间分类。
- `plan --dry-run`：输出确定范围、保留理由、可回收项和计划版本。
- `apply --plan <id>`：重新核对计划条件，在本轮受管环境执行；不能接受任意 shell、根路径或 Docker 名称。
- `pin/unpin`：受信任操作者显式保留对象，记录审计。
- `restore <archive-id> --new-target <managed-target>`：验证并恢复到全新受管目的地。

无明确 apply 参数时默认只读。环境配置选择必须显式且受验证，不得省略参数后回退到正常网站运行配置。

### 9.2 API 与 UI

建议新增只读 `GET /storage`、`GET /jobs/{id}/storage`，并通过现有 bridge 白名单精确暴露；路径命名可调整，但不能做任意文件管理接口。

返回内容建议包括：

- `measured_at`、measurement_scope、是否过期/估算；
- 原始唯一内容、暂存、候选、证据、归档的逻辑字节；
- 可测时返回分配空间与 Docker 报告大小，未知时为 null；
- 共享字节、独占字节、引用字节分别表示，跨 job 合计不重复计算同一 blob；
- retained/archiving/archived/blocked、保留理由、可回收估算和恢复可用性。

页面只增加简洁的空间/归档信息，使用产品语言，例如“原始文件”“临时处理文件”“已归档”“等待恢复”“空间不足”。不将 container ID、DSN、绝对路径、内部哈希策略展示为用户操作要求。

保留现有 evidence 下载的脱敏边界，不通过浏览器直接下载含私有 container inspect 的完整恢复包。本轮不做浏览器删除数据库或任意恢复按钮。

旧后端没有 storage capability 时，页面正常降级，不报错、不阻止上传。统计使用台账/有界缓存，不能每次页面轮询都递归扫描全部 artifacts 或阻塞导入。

遵守 AGENTS.md 的 Next.js 本地文档与单预览服务约束；不额外启动多个网站端口，也不改写当前正常网站到新测试数据库的绑定。浏览器验收优先在同一预览服务上使用可验证隔离的测试路由；若无法无干扰接入，执行组件/bridge 验证并明确标记完整页面上传未验证。

## 10. 测试 session 收尾与统计

把管理能力接入现有工具，避免另建一套平行验收框架。读取现有工具后，提取共享 session 的创建、资源登记、正常关闭、证据保存与 finalize；ACT、knowledge、通用回归入口保留各自的数据核对逻辑。

新测试启动必须显式选择策略，记录在 session manifest；正常现有环境的自动清理默认关闭。提供明确的保留完整环境选项，不能让所有工具再次默认为“全部永久保留”。

覆盖完整 session 和共享数据库两种场景：独占 volume 可按策略归档清理；共享基础设施只能处理自己已证明独占的文件/工作资源，第一版可以保留共享数据库部分并解释。

每阶段记录 wall-clock 起止、CPU/子任务累计时间（若可测）、原始/输出/暂存字节、归档字节、回收对象数和维护用时。累计并行时间不得混称为总耗时。

区分三个空间口径：

1. 文件逻辑大小；
2. 宿主文件系统实际分配/可用空间；
3. Docker 引擎报告的卷/镜像大小。

不能将三者相加作为“释放空间”，也不能把硬链接/写时复制的 `stat.size` 相加宣称真实占用。报告统计能力与误差边界。

空间不足与维护阻塞必须有明确 machine-readable code，经已有错误分类机制标记为系统/环境问题；不要消耗 Agent 轮次去修复磁盘或压缩故障。

## 11. 验收数据与执行方式

本轮验收对象是存储生命周期，不是新来源泛化能力。

1. 先使用小型合成 fixture 验证事务、生命周期、归属与故障；不得用真实主库代替测试依赖。
2. 使用已保存且已验证的数据与 adapter 做完整正常链路回归。可以使用已有 TAS 632 行材料，但明确这是固定材料/已验证 adapter 回归，不是新的未知来源自主学习成功。
3. 为十次上传测试构造可复制的受控 workload，包含同字节同名和同字节改名。全部使用正常上传 API，不直接写 jobs/files 冒充上传。
4. 第一次可发布；其余九次应正常执行该路径要求的样本、全量、独立 QA、注册并返回 `no_change`，保持同一 batch/release。不得为加速测试直接短路到成功状态。
5. 初次启动测试依赖可用已知材料预置经验证的 adapter，但必须经过正常注册/读取边界并披露；不能在实际产品代码硬编码 TAS 字段、文件名、条数或来源特例。
6. 全链路对照只比较同一源码下 storage 功能关闭/开启的等价输入与输出。不能把旧版本曾通过的结果当作当前版本已通过。

大型合成 payload 用于衡量存储去重时应与业务 fixture 分开说明，防止将“占用测试通过”包装成真实事故数据质量通过。

### 12.1 空间验收口径

不要求凭空承诺“所有数据节省 90%”。至少报告：

- 关闭/开启功能下的同一受控 workload；
- 第 1、2、5、10 次上传后及维护完成后的空间快照；
- 唯一原始字节、上传暂存、执行输入、输出、证据、归档、测试卷分别的变化；
- 同一原始 blob 的长期存储不随上传次数线性增长；
- 已回收暂存目录/QA 工作文件不随轮数累积；
- 正常展开环境数量上限生效，保留例外有引用或 pin 依据；
- 归档和每次必要审计记录仍有增长，量化并纳入预算，不能谎称总空间零增长；
- 压缩/验证/恢复额外耗时，确认空间收益没有造成无法接受的重复全盘扫描。

不得以事后手工删除测试目录的方式让空间验收通过。被测系统本身须产生收尾记录并完成允许的回收；验收工具自己的临时恢复副本可由其自身清理。

### 12.2 当前网站数据保护证明

开发前后保存保护清单与哈希，至少包括已有原始上传、配置、最新验收证据及被约定保护的源文件；避免向输出打印 DSN、token 或私有 env。

如正常主数据库可在不启动/重配服务的情况下只读访问，可核对 instance、current release、各 source batch 和确定的计数/查询摘要。若不可用，明确报告“未做主库内容比对”，不能仅凭文件哈希声称全表一致。

测试环境自身的数据库内容核对是必需项，不受主库连接不可用的影响。

## 13. 执行上限与停止条件

本任务以一轮可复核交付为单位，建议并作为本任务默认执行上限：总工作窗口 120 分钟，进入集成验收后的窗口最多 30 分钟，以先到者为准。开始时记录绝对时间和停止时间；不是每次遇到失败重新计时。

只做一批限定集成验收；若发现范围内的小修复，最多两次有证据支持的局部修复与相关重跑。不把“重复尝试”作为进展，不自动延长目标。

出现以下情况应保存当前成果并暂停相应工作：

- 无法证明清理对象属于本轮，或必须修改正常网站配置/数据库才能继续；
- 需要放松独立 QA、证据、发布身份或输入隔离才能通过；
- 需要新增来源适配、在线下载或数据模型调用；
- 相同失败在无新证据下重复，或触及上述时间/重跑上限；
- 归档与恢复链路不能可靠完成，且无法在限定范围内修复。

若只是进阶项未完成，应优先交付已验证的 P1/P2 闭环，逐项写明其余状态；不能把部分完成写成整轮通过。

退出时仅停止本轮自有服务/worker/executor/恢复容器；按已验证策略保留或归档本轮数据。不要暂停/停止当前网站、其他线程或其他项目。不要新建周期自动化。
