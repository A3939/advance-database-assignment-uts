## 4. 已复现问题及证据等级

以下是只读检查中运行原函数的内存反例，没有启动服务、写数据库、创建模型任务或证明沙箱逃逸。执行者需要把它们变成真实小 fixture 回归。

### 4.1 F1：一个已识别类别就授予整表 adapter 权限

起点 `scope_policy._review` 的判定大意：

    accepted = located_context OR (recognized_outcome_count > 0 AND has_key_binding)

默认动作包含 adapter。对完成扫描的剖析输入：1 条识别出的事故类别、999 条其他类别、无定位解释，原函数返回：

    relevance = relevant_limited
    actions 包含 adapter
    recognized_outcome_rows = 1
    other_outcome_rows = 999

问题是相关性标签降级了，实际动作资格却没有对应收窄。不是要求所有值都正确，而是不能仅凭一个词使整份疑似订单/混合内容获得转换资格。

### 4.2 F2：说明正文必须含上传文件名

起点 `scope_policy.explanations` 在已经检查引用指向实际资源、表和字段后，还要求引文正文同时包含字段名和 `file['name']`。

例如引用准确说明：

    CSEF Severity: this field codes road crash severity; 1 means fatal crash.

上传文件名为 `upload.csv`。虽然字段含义明确，且引用声明指向该资源，仍因正文没有 `upload.csv` 而失败。

官方字典通常不会知道用户上传时改过的文件名。文件名不是内容语义或官方身份的充分凭据，不应成为这种字面要求。

### 4.3 F3：上一轮 L2 将已知缺口混入成功条件

旧 L2 使用缺日期的合成事故和陌生编码，又不具备官方身份或具体研究发布授权。官方 SDK 缺日期能力尚未完成。直接执行很可能正确停在已经知道的缺口。

这适合测试卡点识别，但不足以证明“Agent 作出新判断 → 程序执行并验证”的目标。因此本轮先建立合法的**候选验证终点**，再使用有独立 oracle 的真实案例，不为消除缺口预填最终映射或伪造发布收据。

## 5. 工作包 A：修复范围权限，继续宽容合理数据

### 5.1 动作必须与证据强度相符

复用现有 scope 状态和 per-file/table/field grants。不要只改 relevance 的字符串。

| 情况 | 可继续的动作 | 不能自动获得 |
|---|---|---|
| 结构可安全读取，相关性尚不清楚 | 宿主元数据、有限样本、字段分布和定位材料检查 | 整表 adapter、任意候选预处理和无关代码 |
| 有合理道路用途，但存在混合/损坏/未知含义 | 与问题直接相关、字段及输出受限的诊断；必要时 Agent 解释 | 未说明范围的整体转换授权 |
| 资源用途、grain、必要字段语义或已验证来源/配方足以支持转换 | 明确资源/字段/目的的候选执行，随后独立 QA | 官方身份、发布权限、历史替换或删除权限 |

不增加“一律 95% 才相关”“只许 1% 缺失”等业务阈值。类别比例只是调查线索：

- 合法事故表有一个新编码、缺日期或坏坐标，已有来源/字典/结构关系足够时，仍允许适用转换。
- 大量订单状态中夹一条 Injury，没有其他依据时，只能做必要的有限检查，不能赋予默认 adapter。
- 文件全是数字编码但有适用字典与资源关联，不能因识别字符串为 0 拒绝。
- 辅助天气表包含无事故日期、聚合表没有事故 ID，继续采用已建立的用途和关系判断。

当范围只能证明到某个表或字段集合时，资格只到该范围；不要把样本或某一行的证据推广给整包附件。若确有混合数据，应先解释分组/范围，或只允许相关诊断；不得静默删掉看起来不相关的行。

### 5.2 防止换动作名绕过

至少同时核对 adapter、candidate_preprocessing、run_diagnostic 各种别名及可读取表/字段。不能修复 adapter 后，通过把 purpose 改为 candidate_preprocessing 获得等价的无限计算权限。

保持生成代码的既有隔离、无网络、只读输入和累计成本。有限检查可宽容，但无关请求不能仅靠上传一个自写的“道路相关”解释获得不受控工作。

### 5.3 证据输入不是新硬门槛

不要要求每个 CSV 都必须有字典或必须先完成完整官方认证才有调查资格。已知 adapter、已验收 profile、明确粒度及多项一致语义线索都可作为依据；记录实际依赖和限制即可。

不追求不可证明的“识别全部伪装”。本轮重点是修正已知捷径，并保留合理未知数据的小成本调查机会。

## 6. 工作包 B：修复文档绑定，不再依赖文件名字面出现

### 6.1 分开标识与正文

允许本地上传文件名与发布者资源名不同。绑定至少保存：输入内容身份、表/字段身份、解释文档 hash、精确 locator、适用资源/版本关系及宿主核对结果。

可复用现有官方资源 ID/目录记录、来源配方、表头对应、字典中字段/编码结构和文档资源关联。用户或模型声明可作为候选链接，必须由宿主核对其指向和内容；只写一个 resource 字符串不等于证明其适用。

去掉“正文必须出现上传 basename”的检查；同时不能退化为“正文含 road/crash 就通过”。正文没有直接重复字段名时，也可通过既有表格标题、字典行、结构化属性路径等建立精确字段关系，避免制造新的字面门槛。

### 6.2 兼容与失效

- 同字节 CSV 只改文件名，相关性和字段解释不应改变；结果记录新的上传身份，不能继承旧权限。
- 文档来自另一个不相干数据集，即使字段同名或含 crash，也不能自动绑定。
- 输入/表/字段/资源适用范围、文档字节或相关 locator 改变时，撤销受影响 grant 并重新核对。
- 新增无关文档不影响已成立的绑定。
- PDF/CSV/文本/JSON 使用现有 locator，不要求用户重写成自定义 JSON。
- 调查解释仍不同于官方身份：用户上传字典可帮助研究，但不能自行升级为官方发布者证据。

## 7. 工作包 C：先准备并验证候选，再处理发布授权

### 7.1 必须解除的错误耦合

现有 `propose_research_candidate` 保存候选后，在运行 generic 处理前要求精确用户发布收据。对于未知最终映射的真实 Agent 案例，这会使“连候选都不能执行验证”与“不能发布”混在一起。

本轮新增或重构为两段职责，优先复用原工具、处理内核和元数据，不建立第二套研究数据库政策：

    prepare / validate research candidate
      → 原件只读 + 任务范围/操作资格
      → profile/政策能力预检
      → 隔离候选输出 + 现有独立 preprocessing QA
      → 宿主写入 verified candidate receipt
      → 已有有效发布授权：交既有 publisher
      → 没有发布授权：保存已验证候选与具体选择，零发布副作用

**准备与验证权限不能等同发布权限。** 本轮用户已要求在隔离环境处理任务相关数据，不必为了读取两行 fixture、规范化 null 或运行独立 QA 再请求发布批准。

### 7.2 不能通过伪授权实现

- 不伪造 `_research_authorization`，不把模型 `confirmed=true` 当用户批准。
- 若现有 process_bundle 在入口检查发布授权，重构为可信可复用的“候选处理内核”和“有授权的发布入口”；不要复制一套弱化 QA 的旁路。
- generic parser 中为兼容词汇而使用 confirmed，不得影响实际 authority 校验。
- 验证阶段只写本轮 task/work_dir 的受控派生产物；不写正常 release、不注册为官方来源，不触发 publisher。
- 新的 verifier/reader/宿主代码不能由数据 Agent 临时安装；本轮维护代码修改照常独立测试和版本化。

### 7.3 精确版本和候选收据

候选身份至少绑定：

- job/attempt 与原始目标、当前任务模式；
- 输入 hash、表/字段和范围 grant；
- profile、预处理政策、代码/算子、相关证据和执行环境身份；
- 处理结果 hash、原行去向、独立 QA 身份与状态；
- 质量/能力限制、官方身份 false、发布状态 `not_published`；
- 原目标是否满足，不能因研究候选完成把官方接入目标改为 true。

候选变化使对应 gate 失效；旧 receipt 不得发布新 profile。允许同一次活动任务内查询已验证候选而不重新跑计算；跨任务重用必须重新取得范围权限，fresh QA 按既有规则执行。

QA 不只检查模型输出字段存在：使用原始输入独立复读、行去向及手算 oracle，保留未知日期、未知人数、native 类别和源键。模型提供的最终映射不能成为测试唯一的 expected。

### 7.4 与现有 coordinator 衔接

复用 `advance_candidate` 或提供同一入口下的 candidate kind/intent。官方 canonical-v2 与 generic research 的适用 gate 可以不同，但每种路径的实际 gate 必须明确。

- canonical-v2 的 sample/full、独立 QA、注册/发布要求不削弱。
- generic research 复用其已有全量处理与独立 QA；不要为了统一界面伪造它没有执行的 sample 或 registry 收据。
- Agent 提交候选后，由程序完成固定的准备和验证动作；模型不需要逐项发起 parser、QA、读计数或轮询进度。
- 有新语义/QA 问题才返回同一 Agent。修复后继续当前目标；取消、预算和完整性失败继续终止。
- 工具 schema、runtime 指令、workflow state 和 SDK 同步更新。不能实现了新接口，却仍让旧 prompt 要求“一定发布才算完成”。

### 7.5 候选验证必须有真实终点

在明确的 `candidate_validation_only` 等宿主任务模式下，完成独立 QA 后，应产生可信的终止结果。具体命名适配已有状态系统，不必迁移正常业务枚举。

此模式必须由当前用户请求/可信 harness 配置选择，不能由模型随意修改一个失败导入的目标。目标为正式导入的普通任务仍保留原目标，未获授权时只形成受限结果。

实现要求：

- host receipt 证明“本次候选验证目标已完成”，publication 明确为 false。
- runtime/harness 可以据此停止模型，而不是继续追问“为什么没有发布”。
- 不借用 `s.ready` 或 `succeeded` 的既有发布含义伪造已提交状态；若沿用 needs_input，详细 outcome 必须区分“候选已验证，待发布授权”与“候选本身无法处理”。
- 单纯生成 profile、保存提案、返回“需要用户确认”而没有真实执行/独立 QA，不算本轮闭环完成。
- 验证产物继续受保护，模型摘要不能改写 QA；成功后重复请求返回同身份结果，不重复昂贵操作。

## 8. 工作包 D：关键节点的决策和审计

本轮不重造 Agent。保留现有 session、工具桥和累计额度。

decision packet 至少包含当前问题、阶段、candidate revision、原目标、实际未决点、已验证事实、相关引用、已经尝试的方法、允许动作和剩余额度。增加研究候选模式及正确停止条件。

每次真实模型调用记录触发原因与对应阶段。下列动作默认不调用模型：重复读取 workflow 状态、已知规则预处理、固定 QA、结果计数、模型完成后的固定验证、没有新事实的重复失败。

下列情况可交 Agent：陌生编码和字段含义、合理相关性需要解释、存在不同有依据的候选规则、新的 QA 失败或真正工程问题。不要为节省 token 把这些一律标成 unsupported。

不引入固定“最多两次 Agent 介入”的产品规则；继续遵守原累计预算。针对本轮实验，只允许一个案例的一次初始真实运行，不得用新任务重置实验范围。

审计信息应准确：

- `agent_new_judgment` 来源于本次实际决策记录；不能无论何种入口都硬编码 false。
- applied rules 记录实际触发/执行规则；可支持的政策列表单独命名，不把 PP01–PP17 全列成实际应用。
- profile 命中、纯诊断缓存、执行输出复用、fresh QA 分别计量。
- 用户/来源材料、Agent 建议、宿主验证结论的信任等级清楚区分。

这些审计调整限于本轮闭环直接涉及的字段，不扩大成通用成本平台或全站 UI 重构。

必要 L1 最少化：一条几行研究候选的 parser→QA 链和一次明确独立数据库的“没有发布授权则零发布副作用”检查；C4 可合并现有小型发布节点。若执行隔离/投影未改，不重建镜像或重复全部容器探针；若改了，补一个合法和一个越权节点。

每批执行前写下节点和风险，失败后只复验失败及直接受影响节点。不要重跑之前全部 40 项、整个 Python/数据库 suite、完整 ACT、完整 SA 或整站构建。

## 10. 一次最小真实 Agent 验收

### 10.1 开始前的必要条件

只有满足以下条件才启动本轮唯一真实运行：

- A–D 的对应零模型测试通过，未解决的是模型是否会正确理解并使用工具，而不是已知缺少 parser/QA/停止状态。
- 一次明确标注为替身的端到端候选验证演练已证明：候选可以实际完成独立 QA，且没有发布授权也能正确终止。
- 模型环境、私有 gateway、TestSession 所有权、executor 身份、候选源码和输出目录确认可隔离。
- 独立 oracle 已准备好；不再使用 `--oracle none` 作为通过标准。
- 当前正常业务库、Studio、release 不参与写入；不占用正常 3100 或正常模型 gateway。
- 沿用已有合法模型/推理配置与总额度，不提高预算、不切换模型来制造低成本结果；不要输出密钥。

如果任何一项缺失，继续最低成本实现/排错，不启动真实模型来“看看会发生什么”。只有实际缺少用户信息或隔离无法成立时才提出具体阻塞。

### 10.2 案例内容与可见信息

使用两条小型、明确标为 synthetic research 的道路事故记录，可靠原生 ID、一个缺日期、陌生严重度编码，并提供可精确定位的原始字典。字典不包含用户上传文件的 basename，以同时覆盖 F2。

可复用旧 scenario 的素材，但修改为新任务目标和本轮版本并记录父/子 hash。**不能预填最终 profile、类别映射或 adapter 作为模型答案。** 原始字典是应交给模型阅读的事实来源，独立 oracle 是测试侧的期望，两者角色分开。

模型可见：原输入、原字典、研究候选验证目标、合法工具和已有一般政策。模型不可见：测试预填的完整映射答案、伪官方文档、伪发布收据或 oracle 私有路径。

优先目标：

    解释这个研究数据的编码，保留原始 ID、未知日期和未知人数；
    提出适用候选，交程序完成转换与独立验证；
    返回已验证但未发布的研究候选及其限制。

这是 `controlled synthetic source + real Agent`，不是新官方来源验收，不证明 ACT 官方身份。

### 10.3 成功标准

必须同时满足：

1. 真实模型实际读取/引用相关字典并提出候选，未由开发助手提供最终答案。
2. 真实受控工具执行候选；固定步骤由程序推进，模型无需逐步发起整个 ETL/QA。
3. 独立 QA 与测试 oracle 核对两个原始 ID、总行去向、一个未知日期、类别和人数 null。
4. 未知日期的记录未被删除或赋予伪造日期；Fatal 等类别不推成人数。
5. host 产出可核对候选验证收据，模型在正确目标完成处停止。
6. 官方身份 false，发布 false；没有模型 confirmed、自签授权或正常库副作用。
7. 模型调用原因、阶段、工具、usage 和重复操作记录完整；没有二次任务或增加额度。

若原任务状态仍是 needs_input，必须有独立的“候选真实已验证、仅待发布授权”证据才可将本测试的候选验证目标记为通过。只有一份保存的提案、或者停在缺 reader/QA/存储能力，记 incomplete，不算成功。

本轮不要求真实 Agent 证明所有 QA 修复分支；如果案例一次正确完成，也只能声称已验证其语义协调与交接。受控失败/修复分支由 L0/L1 覆盖，不能夸大为真实模型已自愈所有问题。

### 10.4 次数与失败处理

- 一次初始真实运行，同一任务内按正常策略允许必要的多轮 Agent 交互，累计原预算不重置。
- 候选验证成功立即结束，不让模型继续讨论官方发布、地图或跨版本能力。
- 失败保留该次全部证据。可继续只读定位、修改代码和零模型 fixture，不自动启动第二个真实运行。
- 模型传输失败或用量不明也保留事实；不能把失败当“没算一次”反复重开。
- 再跑真实模型、更换案例、扩大数据或启用完整回归，需用户明确进一步范围。

### 10.5 零模型复用检查

真实运行若成功，可对其已验证候选进行一次程序性复验：输入和政策不变时重用合格的准备信息，并完成应有的 fresh QA；记录模型调用为 0。

新任务不得借用旧任务的 scope/发布权限；任务内缓存读取与跨任务 fresh QA 分开报告。若当前只能做到任务内结果幂等读取，不得称跨任务复用已验收；用零模型最小 fixture 补齐接口或记录具体缺口，不再调用模型。

## 12. 实施顺序与完成判定

### N0：基线与最小定位

只读确认候选/正常文件哈希、当前任务和源码加载边界。建立新交付目录和可核对源码链。在真实小 fixture 上复现 F1/F2，不开展全量测试。

### N1：范围与解释修复

完成 A/B 及直接回归；保持宽容诊断，转换资格与相关性证据相符。完成前不得进入付费验收。

### N2：候选准备、验证和 coordinator

实现 C/D：无发布授权也能准备与验证；可信的候选终点；tool schema/runtime/SDK 一致；必要的精确 revision、依赖和审计。完成受控替身和真实程序的最小 L1。

### N3：本轮唯一 L2

所有第 10.1 节条件成立后，执行一次真实 Agent 案例。它的目标是已验证未发布候选；正常服务和 release 不变。若成功，做所需零模型复验；若失败，保存证据并用零模型方式定位，不自动再跑模型。

### N4：交接及后续计划

交付完整实现和实际验收状态。L2 未通过则明确“实现与零模型验收完成，真实协调链未通过/未完成”，不能因为模型调用已发生就写成已验收。

后续正式集成、必要构建/浏览器、扩大回归属于下一维护阶段，准备计划但不自动执行。全套官方 SDK 未知日期和独立人员表等继续保留独立 backlog，不成为本轮零模型任务无限扩张的理由。
