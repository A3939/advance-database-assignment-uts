# ARSIA 代码、架构与规则审查报告

审查日期：2026-10-03（Australia/Sydney）。审查对象：当前本地工作目录，而不是 Git HEAD 单独代表的版本。

**结论：ARSIA 已经具备真实导入、独立 QA、版本化发布、隔离执行和研究工作空间，但安全与正确性规则尚未在所有入口统一。应先修复发布入口分叉、宿主故障分类和测试隔离，再扩展新的来源与自动修复能力。当前不能把它描述为“所有官方来源已支持”或“全项目验收通过”。**

本报告列出本轮发现的全部问题、风险和能力缺口，共 40 项。它不是“任何输入、任何并发与任何部署条件下都已穷尽缺陷”的保证。没有证据支持的问题不作既成事实陈述；已经修复的历史问题单独列明。

## 4. 具体缺陷与冲突

### F01：未知宿主执行异常被交给 Agent 修 adapter

**证据：**[execution_blockers][cap13]、[执行器异常封装][executor246]、[Agent 分流][agent316]。

默认分类为 adapter_revision；trusted_host 分支仅处理几个特定异常类型，没有未知宿主异常的 system_fault 兜底。宿主 RuntimeError 经执行器封装返回，与直接抛出同类异常的行为不同。

本轮直接执行原有两个纯模块得到：

| 输入 | 实际分类 | 要求系统处理 |
|---|---|---|
| trusted_host / RuntimeError | adapter_revision | false |
| trusted_host / ValueError | adapter_revision | false |
| trusted_host / FileNotFoundError | environment_dependency | true |
| adapter / RuntimeError | adapter_revision | false |
| 直接 RuntimeError | system_fault | 是 |

执行器中“只读输入发生变化”“只读 adapter 改变”等完整性异常就会抛 RuntimeError。这不是普通字段 mapping 错误，继续让模型改候选无法修复宿主根因。现有预算仍限制循环，也未发现该问题直接绕过 QA 发布。

**建议：**以可信 origin 为第一层边界，未知 trusted_host 异常默认停在 system_fault；保留原始类型、错误码及证据。由明确的可信分类器列出少量可由候选修复的例外。

**验收：**直接异常、executor envelope、Session、Bridge 路径得到相同分类；宿主完整性失败不进入下一模型修订回合；adapter 自己的 RuntimeError 仍可按既定预算修复。最新[修订循环报告][repairreport]也明确记录 C04/L03 未完成。

### F02：手工 generic 导入与自动准入来源共用发布身份

**证据：**[generic profile 校验][generic56]、[处理分流][processing51]、[旧发布器][worker72]、[正常 Imports][imports39]。

generic-v1 只要求 confirmed=true 及非空 publisher/source_evidence/licence 等字段；它禁止 official_ 和 syn_ 前缀，但没有禁止使用已有自主来源的普通 source_id，例如 tas_cdm_crash。

该路径运行自己的校验，再由 worker 的旧发布器更新 sources[source]。它不进入 autonomous 发布器的同等来源身份、合同兼容、完整性及删除授权链。因此一个人工确认 profile 可以选择已经存在的自主来源身份，并替换该来源当前 batch。

人工映射本身可以是合法功能，问题在于**较低证据等级的入口能更新较高证据等级的同一个发布身份**。界面中的“LOCAL TEST”不构成隔离，因为正常 Imports 已连接 Overview/Analytics/Studio。

**建议：**统一最终发布准入接口；显式记录 admission_level 和 provenance。手工来源使用独立身份空间，或必须通过同一来源更新门禁后才能替换既有自主来源。不能只靠 UI 文案保护。

**验收：**在新测试库先发布自主来源，再提交同 source_id 的 generic 文件；应明确拒绝或生成独立人工来源。人工确认不得授予删除历史记录的权限。本轮未写数据库验证这一场景，结论来自完整静态调用链。

### F03：pinned native 旧包重传可以绕过新发布器的防回滚

**证据：**[native 分流][worker179]、[native route][native53]、[旧发布器指针更新][worker87]、[新发布器历史重放处理][publication347]。

新版 native revision 可以通过自主准入更新 official_* 来源；而精确匹配 pinned 输入仍回到旧 native 路径。旧发布器仅在“匹配 batch 已经是当前 batch”时返回 no_change。匹配到历史 batch、或者以新实现身份重新生成旧内容时，会再次更新当前来源指针。

触发场景：A 为旧官方包，B 为已准入新版本；当前为 B，再上传 pinned A。旧路径缺少新发布器的 historical_input_replay 与更新覆盖/移除门禁，可能把当前视图切回 A。历史 release 本身仍保留，问题是当前指针及可见覆盖倒退。

**建议：**native/generic/autonomous 最终进入同一来源更新政策；恢复历史版本必须是单独、显式的产品操作，不能由普通重传隐式执行。

**验收：**在隔离库覆盖 A→B→旧 A，以及“旧输入但处理实现版本变化”两种情况；普通重传都保留 B。不要仅测试自主发布器内部的 A→B→A。

### F04：默认浏览器测试并不隔离业务写入

**证据：**[Playwright 默认地址][playwright]、[真实 Imports 测试][testimports]、[Studio 测试][teststudio]、[Imports 路由选择][imports39]。

默认 npm run test:e2e 使用 127.0.0.1:3100。imports.spec.ts 访问 /imports，真实上传 browser_fixture、恢复任务并发布；后续直接调用 /api/imports/jobs。它未要求显式 opt-in 或测试实例标识，也未使用 /imports/test。

studio.spec.ts 同样通过真实 /api/studio 创建研究，结束后 archive，并不是删除测试数据或切换隔离 SQLite。反复运行还会消耗研究总数上限。

**影响：**按 README 的普通验证命令运行，会改变当前本地 release、任务历史和 Studio 内容。独立浏览器 profile 只隔离浏览器状态，不隔离服务端数据库。

**建议：**只读 UI 测试与真实写入测试分组。所有写入组要求专用实例、独立数据根与数据库，并在开始前验证标识；无法确认即跳过/失败。隔离页面和隔离服务绑定要一起检查。

**验收：**默认 E2E 不发送导入/Studio 写请求；显式集成测试只能命中测试标识对应环境；正常 release 和 Studio 清单前后不变。

### F05：Node 运行要求与 Studio 实现不一致

**证据：**[README Node 20.9+][readme15]、[Studio 的 DatabaseSync][studiostore]、[package.json][package]、本地 @types/node 的[sqlite 模块声明][nodetypes]。

Studio 使用 node:sqlite，而本地 Node 类型文档标明该模块始于 v22.5.0；README 允许的 Node 20 系列不能满足它。package.json 又没有 engines 约束，因此安装时未必能阻止错误运行环境。

**建议：**选定一个实际验证过、满足 SQLite 功能的 Node 版本范围，在 engines、开发说明和检查命令中统一。不要只写“最新 Node”。

**验收：**支持版本能运行 Studio；不支持版本在安装/启动预检时给出清楚错误。本轮未切换或安装 Node。

### F06：Python 打包清单没有覆盖时区资源

**证据：**[pyproject package-data][pyproject]、[trusted implementation 导入时读取][qa24]、[时区实现][timezone]。

package-data 只有 profiles/*.json、profiles/*.md、knowledge/*.json、knowledge/evidence/*。按实际目录 glob 展开，以下文件均未包含：

- knowledge/timezones/manifest.json
- knowledge/timezones/windowsZones.json
- knowledge/timezones/tzdb.zip
- knowledge/timezones/CLDR-LICENSE
- knowledge/timezones/TZDATA-LICENSE

trusted_qa 在模块导入时就计算这些资源的哈希。源码目录运行和 Docker COPY 可以正常，不能据此证明构建后的 wheel 包完整。

**建议：**显式纳入运行资源与许可文件，用 importlib.resources 或等效的包内资源定位；增加“构建 wheel→新环境安装→离开源码目录导入”的交付检查。

**验证边界：**本轮确认的是声明缺项，未构建/安装 wheel；是否受本机残留打包清单影响必须在干净构建中验证，不能声称已亲测安装失败。

### F07：Studio 配额计算有两个相互独立的错误

**证据：**[write][studiowrite]、[saveTransfer][studiotransfer]。

第一，SQLite length(TEXT) 返回字符数，Buffer.byteLength 返回 UTF-8 字节数。现有统计混用两种单位。内存实验中，100 个“中”字的 length(doc)=100，真实字节数=300。

第二，更新 study 时先统计所有旧文档，再加上完整新文档，没有减去即将被替换的旧版本。假设已用 253 MiB，旧 study 4 MiB、新 study 仍 4 MiB，现公式得到 257 MiB 而拒绝，实际替换后仍应是 253 MiB。

**影响：**非 ASCII 内容可能被低估；临近上限时，等大小甚至缩小的更新、归档或运行收尾也可能失败。数据库/WAL 物理体积还应与逻辑内容配额分开定义。

**建议：**统一统计 BLOB 字节长度；更新使用事务内净增量；快照、附件、transfer 统一配额入口。

**验收：**中文/emoji、多字节附件元数据、等大小替换、缩小、扩容、事务回滚均有边界测试；明确 256 MiB 是逻辑预算还是物理空间承诺。

### F08：达到 64 次分析后，重试现有失败 run 被提前拒绝

**证据：**[beginRun][studiobegin]。

代码先判断 runs.length>=64，再进入 retryId 分支。重试本来会复用原 run，但在第 64 个 run 失败时，仍被“创建新研究”限制拦截。

**建议：**先识别合法重试，再仅对新增 run 应用数量上限；保留现有单 run 重试次数限制。

**验收：**64 个 run 中存在失败项时可以在次数预算内原位重试；新增第 65 个 run 仍拒绝。

### F09：Ask AI 转存 Studio 的幂等性只覆盖同进程同时请求

**证据：**[createStudy][studiocreate]、[linkTransfer][studiolink]。

Map 用于同一进程的并发合并，但 create study、begin run、复制附件/事件、完成状态、linkTransfer 分属多个操作。进程在创建之后、关联 transfer 之前退出，或中间发生错误，会留下没有 transfer 关联的研究。再次请求相同 transferId 可能创建第二份。

错误分支保留不完整研究有利于诊断，但缺少持久化的“这个 transfer 已经占用这个 study”的恢复身份。

**建议：**数据库内先原子 claim transfer→study，状态机记录 transferring/complete/failed；重试恢复同一 study；外部附件复制作为可恢复步骤。

**验收：**逐个断点终止新隔离进程，重启后同一 transferId 仍只对应一个 study。此故障窗口为静态分析，未在现有 Studio 注入故障。

### F10：registry 搜索的州过滤发生在 LIMIT 之后

**证据：**[registry.search][registry81]。

SQL 只按 source_id 过滤，取最新 30 条；随后 Python 再过滤 jurisdiction。如果某州的有效 adapter 位于全局第 31 条以后，按该州搜索会错误返回空。

**建议：**把 jurisdiction 条件移到 SQL 的 LIMIT 之前，并提供稳定分页；区分“无匹配”和“结果被截断”。

**验收：**31 个以上跨州注册版本中，目标州最旧的有效条目仍可被查到。

### F11：recipe 对象随运行身份增长，检索成本与候选上限失配

**证据：**[remember/match][reuse73]、[64 对象限制][reuse457]。

缓存对象包含 file_id、合同、证据本地路径等运行相关值；相同语义的成功重传仍可能产生不同 CAS 对象。match 扫全目录、核对依赖/证据并读取注册记录后，才折叠相同语义结果。

版本候选检索却在整个对象目录超过 64 项时直接返回 VERSION_CACHE_SCAN_LIMIT。这个阈值与“当前来源的有效候选数”无关。只要旧对象累计，就可能使其他来源无法走已有版本候选路径。

**建议：**按逻辑来源、结构、语义、依赖代际建立索引；将 recipe 模板与每次执行审计分离；候选上限作用于筛选后的候选集合。保留审计对象，不以删除历史证据解决检索问题。

**验收：**100 次相同输入/语义重传不会使新版本候选能力失效；大量无关来源不会迫使目标来源重新完整调查；记录命中、失效、歧义及扫描成本。

### F12：覆盖范围扫描逐行触发数据库连接

**证据：**[measured coverage 循环][reuse329]、[Agent cancel_check][agent202]、[worker 取消检查][worker148]、[store.get_job/connect][store58]。

measured coverage 每行调用 cancelled()；在真实 Session 中最终进入 worker 的 get_job。get_job 每次新建 psycopg 连接，验证数据库身份，再查询 job。CSV reader 自己每 1000 行才检查，但外层扫描重新变成逐行检查。

**影响：**N 行输入可产生约 N 次数据库连接与多条验证 SQL，浪费时间并放大超时/预算消耗。这里确认调用复杂度，不提供未经测量的毫秒数字。

**建议：**统一取消检查器：本地停止信号快速检查，数据库状态按短时间间隔节流；在阶段边界和发布事务前仍强制检查，不削弱取消与发布的最终锁保护。

**验收：**10 万行扫描的数据库轮询数量由时间预算决定而不是等于行数；取消延迟仍满足明确上限。

### F13：真实零月份被当成没有月度观测，年度完整性判断失真

**证据：**[查询聚合][query189]、[Web 年度 fullYear][published52]。

查询已经区分完整覆盖区间内的真实零与未知，但 monthly/yearly 用实际存在的事件 GROUP BY，只返回有行的月份。Web 再用 q.monthly 的条目数作为 observedMonths，要求 12 项才判 fullYear。

如果已证明完整覆盖全年、但某月确实没有事故，全年完整性会被误判为不完整；整段为零时 summary 和趋势返回的表达也不一致。

**建议：**从已验证 coverage_intervals 构造时间轴，明确“已覆盖且为零”“无覆盖”“指标未知”。只有具备完整覆盖证明时才生成零月份，不能普遍补零。

**验收：**完整年度中一个零事故月应仍是完整年度；未证明覆盖的月份仍保持缺失/未知；bounded incremental 不可伪造完整月份。

### F14：支持年份在不同层不一致

**证据：**[canonical 日期][canonical121]、[Python query][query131]、[Web filters][catalog44]、[generic][generic56]。

canonical 接受 1800–2200，Python query 接受 1900–2200，Web 本地发布筛选与 generic 接受 1900–2100。符合导入范围的数据可能被查询层拒绝。

**建议：**定义共同的产品日期范围，并从一个契约生成各层验证；若底层有更宽归档能力，UI 必须明确区分可存储与可查询范围。

**验收：**对 1899、1900、2100、2101、2200、2201 做跨层一致性测试。现实近期事故数据不一定触发此问题，因此优先级低于发布缺陷。

### F15：目录服务故障与“尚无本地发布”被混为一谈

**证据：**[resolveCatalog][catalog22]。

未指定 releaseId 时，任何读取异常都会返回 SNAPSHOT_CATALOG。首次打开或未固定 release 的页面，在本地 API/数据库故障时可能显示旧三州快照，而不是当前本地来源不可读取的状态。

显式指定 releaseId 的路径会抛错，这是正确的；问题仅在默认目录解析。返回值中的 mode 可以体现 snapshot，但没有同时表达“因为服务故障而降级”的原因。

**建议：**区分无本地 release、主动选择快照、服务不可用三种状态；保留清楚的降级原因和重试入口，避免误以为导入来源消失。

**验收：**无本地发布可以正常使用快照；已有发布但服务断开时，应明确提示当前发布不可用，不把故障包装为正常初始状态。

### F16：失败模型响应的 usage 缺少 response 级审计

**证据：**[runner 响应事件][runner111]、[model audit][modelaudit]。

只有 response.completed 调用 recordResponse。response.failed、response.incomplete 或 error 直接抛异常；即使响应事件可提供 id/usage，也没有进入同等记录。终态 failed/cancelled 记录不能补回请求级用量。

**建议：**记录每次请求开始、response ID、所有可得 usage 及终态；拿不到 usage 时明确标 unknown，不能当零。与 Imports 的已知/未知统计方式统一。

**验收：**成功、incomplete、failed、网络中断、主动取消都能对账请求数；没有 usage 的请求保留未知项。本轮没有调用模型验证计费。

### F17：默认 pytest 路径与不可重绑定 runtime 规则冲突

**证据：**[新配置绑定][config38]、[旧 test_backend fixture][backend21]、[pipeline README 命令][pipereadme15]。

test_backend 在模块顶层导入 API/store/worker/config；旧 fixture 分支随后创建测试 DB 并改 ARSIA_IMPORT_CONFIG。新 read_config 明确拒绝在首次导入后切换配置，因此后续隐式 read_config 的请求会失败。

ARSIA_REGRESSION_INSTANCE 对应的专用 runner 分支已采用不可变绑定，这是正确路径；但普通 README 仍指导直接 pytest -q，旧分支仍保留。

**建议：**数据库测试统一由新进程、显式 managed runtime 启动；不满足条件时明确跳过/拒绝。不要重新放开运行中配置重绑定来迁就 fixture。

**验收：**文档命令与实际支持的 runner 一致；测试开始前确认隔离，而不是建库以后才因配置错误失败。

### F18：顶层 README 对关键副作用的说明已过时

**证据：**[README 当前能力][readme9]、[README Imports 描述][readme33]、[pipeline README][pipereadme]、[Imports 组件][imports39]。

README 仍称 Imports 仅预览元数据、不上传、不入库、不持久化；称本目录不连接 Python/PostgreSQL；这些与当前实际代码及 pipeline 文档相反。只在末尾追加 Studio 说明没有纠正入口叙述。

**影响：**新协作者可能误判导入、测试、启动和恢复的副作用；也无法正确理解官方快照、正常本地 release 与隔离测试环境的关系。

**建议：**重写当前架构、页面能力、运行前提与验证命令；把旧阶段记录移入明确标注的历史说明，保留历史而不让它作为当前操作指南。

**验收：**首次阅读 README 即能判断哪些操作写哪里、正常页面从哪里读数据、如何进入隔离测试。

### F19：knowledge catalog 混入过时的实现能力结论

**证据：**[ACT 旧 limitation][catalogact]、[RDF grounding 实现][rdf]、[trusted QA 调用][qardf]。

ACT 条目仍写“Existing trusted QA lacks RDF/WGS84 vocabulary grounding”，但当前已有 rdf_geography.prove_coordinates，并被 trusted QA 使用。Agent 查询这个研究知识时可能被引导为“必须改系统”或重复调查。

这不等于当前所有 ACT 文件都已验证；具体输入仍必须通过来源、字段、样本、坐标与上传绑定。

**建议：**把“数据集本身的限制”与“某实现版本当时的能力限制”分开。后者关联 capability/version/test evidence，并可判为 superseded，不能永久存为来源事实。

**验收：**知识库不再提供与当前能力冲突的否定结论；保留历史研究日期与当时限制，不删除原始证据。

## 5. 架构、可靠性与安全风险

### F20：分析 Docker 沙箱的孤儿治理弱于导入沙箱

**证据：**[analysis sandbox 参数][sandbox36]、[finally 清理][sandbox151]、[容器 runner][sandboxrunner]。

分析容器有无网络、只读、内存/CPU/pid 限制，runner 也设置 CPU 时间限制。这些应保留。但墙钟超时和 rm -f 依赖 Next/Node 活着；finally 遇到 SIGKILL 或宿主崩溃不会执行，rm 失败又被忽略。当前参数没有可供受控恢复器识别的完整 ownership 标签与独立墙钟机制。

CPU 时间限制无法终止长期 sleep 的低 CPU 进程。现有 Imports 孤儿治理不能自动推导覆盖此独立 analysis 命名空间。

**建议：**给分析任务增加可信 owner/attempt receipt、容器内墙钟终止及限定归属的恢复检查；清理失败应可见。不得使用全局 Docker prune。

**验收：**在专用环境分别终止父进程、模拟 Docker 暂不可达和执行低 CPU 长等待，最终只处置自有容器，保留可审计结果。当前未做此故障实测。

### F21：宿主解析器的资源边界仍需补强

**证据：**[XLSX 加载][xlsx131]、[独立 QA 原始读取][qa480]。

生成代码在容器里，但文件探测、部分 Excel/PDF/JSON 解析和 trusted QA 在宿主。XLSX 的压缩包展开上限为 2 GiB；read_only 不表示所有共享字符串/元数据都不会先加载，也不等于有 OS 级内存/墙钟约束。部分解析阶段在库调用内部无法及时触发取消回调。

这是资源耗尽风险，不是已确认的远程代码执行漏洞；现有大小、页数、类型及安全 XML 检查也不能忽略。

**建议：**将高风险解析放进受控只读子进程，限制内存、墙钟、展开体积与返回摘要；QA 仍由可信代码驱动，不把准入权交给模型。

**验收：**压缩比高、共享字符串多、损坏文档、慢解析输入都在预算内失败，主 worker 可继续处理其他任务。禁止用用户原文件做破坏性构造。

### F22：独立 QA 的独立性是“执行与证据独立”，还不是完全独立算法

**证据：**[trusted QA 的 project 引用及重放][qaproject]、[adapter SDK][sdk]。

宿主重新读取输入、对照隔离输出能有效抓住篡改、漏行和生成代码偏离合同。但执行器与 QA 共享 canonical.project、解析/lookup 等实现，若共同函数对一个语义表达理解错误，双方可能一致通过。

**建议：**保留现有重放；为日期、时区、坐标、伤亡人数、lookup 分配、更新范围建立小而独立的人工期望数据集、外部官方统计核对与变形测试。oracle 不应直接调用同一个 project 算出 expected。

**验收：**故意改变一个共享转换规则，至少一个独立 oracle 能失败。不要把“双执行”表述为“所有语义已被独立证明”。

### F23：Ask AI 的数值规则没有完整的结论验证层

**证据：**[Agent instructions][runner40]、[结果计数与 validated 标记][runner198]。

提示词要求数字来自工具、派生计算使用 Python、不得混合州口径。代码证明工具参数通过验证，并记录真实结果，但任何成功工具都会增加 dataCalls；读取目录后即可满足“调用过工具”的最低条件。最终文本没有逐项检查数字、引用是否存在，以及 Python 推导是否真的使用了对应数据。

evidence.query.validated=true 表示请求校验，不是研究结论正确性证明。

**建议：**区分 query_validated、computation_executed、claim_supported。对于关键数字先输出结构化 claim，绑定 evidence ID、指标、来源和区间；前端再呈现文字。自由文本结论保留人工核对边界。

**验收：**无效 E 编号、引用无关区间、凭空百分比、只查 catalog 后报事故数等反例被识别。这里未声称已观察到实际错误回答。

### F24：各 Web 入口的本地请求边界不统一

**证据：**[sameOrigin][sameorigin]、[Imports bridge][bridge]。

Ask AI/Studio 复用的 sameOrigin 在无 Origin 时返回 true；有 Origin 时主要比较来访 Host，而不是统一的受信 loopback Host 集合。Imports 对本地环境的防护更明确，规则分散容易在新增路由时遗漏。

当前应用绑定 127.0.0.1，且没有多用户部署承诺，因此不能直接称为“公网未授权漏洞”。实际 DNS rebinding/代理行为还取决于 Next 和部署层，本轮未测试。

**建议：**集中定义 localhost Host、Origin、写请求来源和未来认证政策，区分服务端内部调用与浏览器写请求；本地单用户边界写入产品约束。

**验收：**合法本地调用成功；跨站写、非允许 Host、伪造转发头和缺失来源的浏览器写请求按明确策略处理。

### F25：Studio 容量达到上限后缺少完整出路

**证据：**[128 研究上限][studiocreate213]、[50 版本上限][studiosnapshot]、[restore 两次快照][studiorestore]。

归档研究仍计入 128 个总数；没有配套的完整导出后移除/恢复流程。restore 会保存 Before restore 与 Restored version 两份快照，在已有 49 个版本时，第二份触顶导致整个恢复回滚。接近文档/存储限额时，恢复和收尾也缺乏预留。

限制本身合理，问题是“请创建新研究”最终也会被全局数量上限阻断。

**建议：**提供容量详情、可恢复导出、显式删除/迁移与恢复余量；达到上限前提示操作所需净空间。不得后台自动删用户研究来解锁。

**验收：**128 个研究、49/50 个版本及存储临界值下，用户有可理解、保留数据的处理路径。

### F26：Studio 数据演进没有显式迁移契约

**证据：**[SQLite 表创建][studiostore]、[全局 Store/HMR][studiolink]。

constructor 主要 CREATE TABLE IF NOT EXISTS；业务主体为整份 JSON。缺少统一 schema version/document version 和逐版本迁移。PRAGMA foreign_keys=ON 也不能替代实际 study_id 外键声明，当前相关表未声明这些引用约束。

**建议：**数据库 user_version/迁移表与 Study 文档版本分开管理；定义兼容读取、升级、失败回滚和备份；补充关联完整性检查。避免以后用 JSON.parse 后默认字段掩盖旧数据问题。

**验收：**真实旧版本研究的升级、重复打开、失败恢复可重复验证；升级不修改业务语义。

### F27：复用依赖按大量整文件哈希绑定，失效粒度过粗

**证据：**[TRUSTED_FILES][qa24]、[recipe dependency 比较][reuse73]。

当前可信实现覆盖 41 项文件/资源，包含 publication、证据、投影、reader 等。对来源无关的实现改动也可能使相关 recipe 全部依赖不匹配，导致重新调查。运行中代码变化拒绝执行是合理保护，不能简单关闭。

**建议：**区分语义规则版本、解析器版本、证据验证器版本、发布策略版本与执行环境；按 adapter 使用的能力建立依赖。只有通过兼容性证明的更改才允许复用旧模板，仍执行新 QA。

**验收：**无关格式能力新增不必使已有来源模板失效；影响当前来源语义的变更必须失效，不能靠人工“版本没变”跳过。

### F28：知识库的结构校验与完成状态还偏浅

**证据：**[load_catalog][knowledge75]、[catalog][knowledgecatalog]。

当前 catalog 有 13 个来源条目、63 个资源，48 个资源 fields 为空。部分为空是字典/报告/尚不可访问资源的合理状态，不能把 48 当作 48 个缺陷。但缺少统一机器可读的字段级 researched/observed/grounded/admitted 状态，容易混淆“找到资源”与“可确定性复用”。

load_catalog 主要检查顶层必填字段、schema_version 和来源 ID 重复；对资源唯一性、grain 枚举、证据引用、字段类型、locator 可达性等缺少同等级完整校验。

**建议：**建立严格 catalog schema 和离线 lint；每项未知注明原因、适用资源/版本与后续最小动作。来源研究事实与运行准入状态独立。

**验收：**错误 resource 引用、重复资源 ID、无效字段证据与过期能力结论能被离线检查发现；research-only 条目不得伪装成 adapter 命中。

### F29：许可状态不应只是一段非空文字

**证据：**[source 基础字段校验][qa323]、[WA 最新报告][repairreport]、[catalog][knowledgecatalog]。

最新 WA 实验中 licence=null 预检失败，改成“该精确图层许可尚未确定”的说明后预检通过。报告如实承认许可未验证，这不是违规行为的证据；它暴露的是字段模型没有区分“许可存在且适用”与“未知说明”。

**建议：**license 增加 status、原文/URL、适用资源、获取日期、允许的处理/展示范围及证据；区分本地研究、持久发布和对外再分发的产品政策。来源文字不应自动授予权限。

**验收：**unknown、verified、restricted、conflicting 的状态可追踪；对精确图层未知的许可，不得自动继承同州另一个数据集的许可。本报告不作具体许可法律判断。

### F30：并发限制与模型预算按入口分裂

**证据：**[Ask AI 路由][agentroute]、[Studio runs][studioroute]、[导入 Agent][agent202]。

Ask AI 和 Studio 各自限制同时分析数及请求频率；Imports 有独立 worker/模型预算。多个入口同时使用时，没有统一的模型调用、活跃容器、累计输入/输出用量视图。进程内计数也不能自动覆盖多个 Node 进程或重启。

**建议：**本地先建立共享资源协调与单任务预算账本，不必立即引入复杂分布式队列。区分模型请求预算、墙钟预算、容器预算和 usage unknown；重试沿用累计预算。

**验收：**多个页面并行时不突破明确总限额；重启不把正在运行的任务当成没有消耗；界面显示有效预算与停止原因。

### F31：读取路径有重复聚合成本

**证据：**[catalog/metadata][query55]、[query 聚合][query189]、[published-data][published52]、[publication cache][publicationcache]。

catalog 为每个 batch 查询元数据，还 count 全部行以判定月度能力；单来源 query 又取 summary、yearly、monthly、severity、地理等结果。前端多个报告共享读取缓存已有缓解，但数据增长后仍会重复扫描，且目录不应随明细体积显著变慢。

**建议：**发布事务产出不可变的能力、覆盖与聚合摘要；按 release/source/规范化查询键共享结果。仅缓存已验证事实，不把 unknown 填成零。先度量再决定索引或物化策略。

**验收：**固定体量的冷热缓存、SQL 次数、p50/p95、取消与 statement timeout 有可重复基线。本轮未执行性能压测，不宣称已有具体响应延迟。

### F33：规则缺少单一“当前状态”入口

**建议：**增加一份当前能力与规则索引：每条规则列实现位置、适用入口、测试证据、状态、被哪份新规则替代。永久安全约束与某次任务的时间/修改次数上限分开，不要求后续工作盲目继承已结束任务的临时计划。

**验收：**新协作者无需读取十几份任务书即可识别有效规则；F01–F03 这类“同一规则跨入口不一致”可通过矩阵发现。

这不是“备份已损坏”，也不否定文件校验；缺的是数据库能否正常启动、迁移、查询并保持 batch/release/registry 引用的一层证据。

**建议：**在后续获授权的隔离环境做抽样恢复演练，核对 manifest→PostgreSQL→关键关系→固定查询。把恢复说明与存储 catalog/历史实验的状态关联。

**验收：**记录实际恢复耗时、使用镜像、SQL 完整性与查询结果；仍不得把主库连接不可用时的文件哈希检查描述为主库全表比对。

### F35：当前实现不能仅靠 Git HEAD 重建

本轮 status 显示 pipeline、Studio、Imports、新测试和文档等大量核心能力未跟踪，已有前端文件也有修改。因此代码审查、回归和发布候选之间容易出现“同一名字、不同源码”的情况。

这不是要求现在提交；用户当前不授权提交/推送，且可能有主线程工作，不能清理或整理这些修改。

**建议：**结束一个开发阶段时生成包含源码、资源、依赖、镜像与配置模板身份的可移交清单；在用户决定后再组织提交。artifact 应标注所对应源码，而不是只记运行日期。

**验收：**在独立目录按交付清单可复现，不依赖未记录的本机旧镜像、绝对路径或临时文件；不包含真实凭据。

### F36：维护边界应按业务能力拆分，而不只是继续新增文件

Studio、Analytics、Agent 等组件较大；Python 的 AgentSession、trusted_qa 与多类 proof/contract 字典跨模块传递，部分规则以重复字符串和嵌套键约定。局部增加一个字段或错误码，需要同时知道 UI、桥接、模型工具、准入和发布消费方式。

**建议：**

- 按纯状态逻辑、请求生命周期、数据展示拆分大型组件；
- 只为关键边界引入强类型/版本化契约，如 executor result、admission、source identity、update policy、blocker；
- 错误分类保持有限且按责任归属组织，不引入一张失控的全项目错误码表；
- 将稳定业务转换保持纯函数，IO、预算、取消与持久化集中在清楚边界；
- 收紧 tsconfig 的源码 include，避免未来 artifacts 中保存的 TS 快照意外进入类型检查。

**验收：**新增一种错误或能力有明确改动清单与跨层契约测试；不以大规模重构打断尚未完成的正确性修复。

### 10.1 产品目标与自动化边界

目标是：用户上传澳大利亚官方道路事故原始文件后，系统自主识别资源与粒度、查证必要定义、制定并执行 preprocessing/transformation、独立验证、集成到统一数据库，再通过网站展示可支持的指标与分析。

自动化应覆盖能够通过现有算子、官方调查和程序校验解决的问题。系统应保存未解决事项的具体对象、原因、已取得证据、责任方及下一步；确需用户信息时只问最小必要问题。无依据的语义猜测不能通过“高置信度”转化成事实。

完成程度分开表达：

- data_received：已接收且身份完整；
- profiled：格式、结构和粒度已调查；
- evidence_grounded：相应语义证据已绑定；
- transformed：转换已执行；
- qa_passed：当前候选通过必要独立验证；
- published：通过来源更新门禁并原子发布；
- website_verified：对应 release 可通过实际网站数据服务正确读取。

这些名称是状态语义示例，应与现有状态机兼容整合，不要求另建一套重复状态系统。状态应注明适用资源、指标和能力，不能要求全部可选能力同时通过；受限接入与阻塞传播按第 11 节处理。运行退出成功、预检通过、知识条目命中、adapter 已注册均不能单独代替后续状态。

### 10.2 架构收敛要求

保留并复用现有 PostgreSQL、Next.js、Codex harness、reader、隔离执行器、QA、来源证据、registry 与存储归属能力。默认不引入图数据库、向量数据库、第二套 Agent 编排框架或大型分布式平台；若确有必要，先给出当前实现无法满足的具体问题和更小替代方案。

所有 native、generic、autonomous 入口必须遵守共同的最终来源身份、候选完整性、更新权限、QA 与发布政策。共同政策按实际操作和能力应用相应证据要求，不是所有字段和功能适用同一最高门槛，也不要求把所有解析代码塞进一个函数。已验证的历史 native adapter 可以保留确定性入口，但必须以当前可核验的证据与身份进入共同发布边界；人工 confirmed 不能提高来源授权等级。

候选包至少应表达下列信息，优先扩展现有合同而不是另造大而全的 DSL：

| 方面 | 必须表达的含义 |
|---|---|
| 输入 | 上传收据、内容哈希、资源角色、解析计划、行定位 |
| 来源 | dataset/resource 身份、jurisdiction、托管授权、版本及证据范围 |
| 语义 | 行粒度、业务键、关联、指标定义、缺失/抑制值与日期/时区/坐标依据 |
| 转换 | 使用的受控操作、参数、依赖版本及可能改变行数的规则 |
| 更新 | snapshot/partition/incremental 的范围、键稳定性、完整性与移除授权 |
| 验证 | 本次执行身份、输出哈希、fresh QA、独立 oracle/限定证明 |
| 发布 | 目标来源、准入等级、历史兼容、候选内容身份与最终 release |

普通上传不能隐式执行历史回滚。发现旧输入重放时按既有防回滚政策处理；恢复旧版应是另一个显式操作，本轮不新增默认自动回滚。

### 10.3 Agent 与确定性程序的职责

- 已验证且无歧义的相同输入/语义：确定性匹配、执行、fresh QA、发布/no_change；不为确认缓存命中再调用模型。
- 已知来源变化：形成结构、语义、版本与相关证据差异包，只把必要变化和可回读引用交给 Agent。不能把“同表头”当成“同语义”。
- 未知来源：Agent 自主调查并提出候选；成功准入后沉淀为可复用模板，运行审计与模板身份分开。
- 系统能力不足：保存缺失算子/格式与最小示例，交给开发处理；仅影响局部能力时按第 11 节确定可继续的独立范围，宿主安全/完整性失败仍停止任务。数据 Agent 不得修改可信 QA、发布器或宿主配置来自行授权。
- 可修复候选错误：在累计预算内修正并重跑受影响门禁；失败 gate 不因无关成功而清除。
- 宿主故障、配置错误、完整性失败、模型传输故障：明确分类；不能伪装成缺少数据字典，也不能反复改 mapping。
- 缺少业务或来源证据：先使用合法公开调查；仍无解时说明精确缺失内容，不编造默认值。

新能力应贯通读取、合同、执行、独立校验、发布和查询。只增加一个 reader 或允许一个字段，并不等于完成该能力。

### 10.4 数据与证据标准

1. 一行事故、车辆/交通参与单位、人员/伤亡、聚合观测必须显式区分。不得用一张宽事故表伪装所有粒度；现有 canonical 多表可以继续使用。
2. 明确 original key、source/version/resource identity 与内部 canonical ID 的区别；缺乏稳定键时不得自动增量覆盖。
3. 格式等价变换与语义变化分开：文件名、列顺序、ZIP 包装变化不应无故制造新语义；字段含义、时区、计数口径、覆盖范围变化必须进入兼容判定。
4. NULL/unknown、unsupported、no_results、suppressed 与真实零应在可适用位置区分；不得统一填零。只有已证明完整覆盖且指标可测的区间才能推出零。
5. 去重、过滤、异常值处置、插补、拆分/聚合都可能改变数据含义。必须有明确规则、作用范围、守恒/分配校验与原行溯源；不能静默丢行或用任意 first/last 解决冲突。
6. 日期保留精度与时区依据；坐标保留 CRS、轴序、转换实现与精度限制。禁止仅按数值范围或州名猜 CRS。
7. 证据保存原始收据哈希、定位、获取时间、适用数据集/资源/字段/版本及授权关系。官方委托托管或引用的标准可成为相应范围证据；既不能只认 .gov.au，也不能把普通网页链接当来源授权。
8. 自然语言 PDF/HTML 可以由 Agent 提取为结构化主张，但提取结果要绑定原文定位，核对适用性和冲突；引文真实不等于解释必然正确。无法独立确认的关键语义保持未决，或进入明确标注的人工审阅路径，不冒充官方自动准入。
9. license 至少区分 verified/unknown/restricted/conflicting，并绑定精确资源；本地调查、数据库持久化与对外分发的适用政策分别说明。
10. 研究事实与实现能力分开版本化。旧“当前不支持”不能作为数据集永久事实；准入状态必须关联实现与测试身份。

这些是项目内部执行要求。涉及具体外部标准、协议细节或许可范围时，开发窗口应核对当前官方原始文档，不凭本节或模型记忆补写规范。

### 10.5 网站与数据库的集成标准

- 原始层保留不可变文件及来源；标准化层保留实体、关系与原值；分析服务按明确定义提供指标。
- 前端由 catalog/capabilities 驱动，复用现有页面，不为每州复制组件或硬编码 adapter 专属展示。
- 网页、Ask AI、Studio 的数据读取固定到相应 release/source/period。发布刷新目录后，历史链接与已固定研究仍保持历史版本。
- 在依赖分析证明其他指标不受影响时，坐标证据不足仅限制地理能力；无死亡人数不能伪造 deaths。允许保留原字段及未决状态、发布明确受限的已验证能力，但必须重验适用范围并保留用户原目标；不得删除失败事实或改名为“全部通过”。
- All 保留来源独立和重叠警告，不自动相加成全国总数；支持来源的既有地图能力不应因新增不支持来源而消失。
- 区分主动选择历史快照、尚无本地 release、后端不可用。后端异常不得无提示冒充“还没有导入”。

### 10.6 实施范围与优先级的使用方式

本报告不是要求对 40 项各写一个新模块。开发前逐项复核，允许合并同根因；已经被其他窗口修复、基于新证据不成立或仅适用于未来部署的条目，要记录结论和依据。

- **必须处理：**F01–F19 中复核仍成立的本地缺陷/声明缺项；发布身份与隔离问题不可推迟给 UI 文案解决。
- **必须收敛：**F20/F21 对当前支持输入与本地运行路径的资源/故障边界；F22 的关键独立 oracle；F25/F26 的本地 Studio 持久性与安全升级策略。
- **必须兼容：**第 11 节的替代证据路径、按能力阻断、字段分级、行去向追踪及 K01–K10 正反例；对实际需要的能力完成实现和验证，不能仅追加“更灵活”的文案。
- **随主链路落实：**F23/F24/F27–F33/F35–F38/F40 的适用部分。至少落实可信状态、规则索引、能力矩阵、来源复用、真实主链路及成本记录；更重的长期架构优化需证据驱动。
- **明确区分：**F34 的真实 SQL 恢复演练是独立运维验收，需有可合法安全使用的备份与独立资源；F39 的 Linux/多用户/公网部署不属于本轮本地产品改造的完成条件。
- 任何保留项记录影响、当前防护、后续最小动作及未做原因。不能仅写“未来优化”，也不能用大量低风险修复掩盖仍开放的 P1。

不得应用迁移到现有用户数据库来证明迁移可用。schema/文档迁移应先对独立旧版本 fixture 或测试副本验证，提供后续显式升级入口；普通页面访问或热更新不能偷偷改写现有研究/发布数据。

### 10.7 隔离验收矩阵

至少选择三类代表性官方资源，覆盖不少于三个州/领地；组合必须包含文本表格、多表文件/压缩包及空间表示。优先利用已有合法原始输入及收据，避免重复全量下载。

| 验收 | 必须证明 |
|---|---|
| 同一文件首次处理 | 原始输入→调查/已有知识→转换→fresh QA→注册/发布→查询→网站读取 |
| 相同字节同名/改名 | 可复用场景 0 次数据处理模型调用，fresh QA，no_change，无额外业务重复 |
| 新版本变化 | 受控新旧输入的差异识别、必要修订、fresh QA 和范围保护；真实官方版本对另列证据 |
| 跨入口来源替换 | native/generic/autonomous 无法通过不同路径绕过来源身份与移除授权 |
| 质量反例 | 重复键、孤儿关联、计数广播、未知/冲突 CRS、日期精度、零与缺失、表示变化等被正确处理 |
| 故障反例 | 取消、提交响应丢失、宿主异常、配额不足、父进程退出时无错误发布及无不受控资源遗留 |
| 网站集成 | 实际 Web 数据服务读测试 release，指标/地图能力/缺失状态正确，历史 pin 不变 |
| Studio | 真实字节配额、原位重试、转存幂等、容量边界和旧文档兼容 |
| 交付形态 | 支持 Node 版本、独立 wheel 安装及与执行器资源/规则的兼容 |

代表性输入不能全部是为适配当前代码人工改写的“官方格式 fixture”。合成/派生材料用于负例、兼容性正例和受控边界；真实官方输入用于来源接入证明，两类结果分开报告。等价变形的派生 fixture 按第 11 节标明转换与原始身份，不冒充另一官方版本。

真实官方版本对取得失败时，保留具体限制；受控版本测试可以验证程序机制，但不能宣称真实跨版本验收完成。如果某类官方输入无法合法取得，完成不依赖它的实现并准确记录未完成项，不绕过登录/授权，不把其他格式当作等价通过。

验证目标是用户主链路，不是累计测试数。独立 oracle 不得调用同一个 canonical.project 算 expected；源文件中的全量键、行数和独立统计检查，以及必要的人工审阅语义，应形成独立证据。已参与调试的来源不能称为新盲测。

### 10.8 运行影响与资源预算

开发前识别当前修改、进程、实例、release 和任务；默认只做必要只读检查，不输出凭据。现有服务不可访问时，不得宣称已完成其状态/内容保护核对。

所有写入测试使用新建、有 ownership marker 的专用目录、数据库、SQLite、registry/cache、队列、输出和唯一镜像标签。数据库名字不同不足以证明完整隔离；上传入口、配置首次绑定、模型网关路由与网站读取目标也必须指向该实例。

复用唯一 3100 预览，不为测试擅自另起端口。正常网页不能切到测试 release，正常 Imports/Studio API 不能接收测试写入。可在现有明确隔离入口或离线服务测试中验证；若某项 UI 验证确实需要重启/切换共享服务且无法隔离，先完成其余独立工作，再提出具体影响与需要的授权。

沿用并记录现有明确的模型/工具/墙钟/重试预算，开发任务与数据处理模型消耗分开。用户未给总 token 预算时不编造 Goal token_budget；也不自动提高旧 session 的固定额度。新真实实验须显式运行，默认测试、页面加载、失败重试不能隐式启动昂贵模型流程。同一根因失败后先离线复现并验证修复，再启动新的受控实验。

阶段收尾只停止本轮明确归属的活动进程/容器，保留日志、原始数据、失败证据和必要恢复材料；无全局 prune、无清空历史 catalog/pin/账本。采用内容哈希去重和紧凑索引，避免每轮复制所有历史产物。

### 10.9 交付与完成判定

至少交付实际代码、直接相关测试、逐项问题处置表、当前架构/能力/规则索引、真实来源验收、迁移与运行说明。可以合并为少量清楚文档；不要为每个动作生成新目录或新报告。

逐项处置表包含：ID、当前是否复现、根因、实现位置、验证命令/证据、状态、未完成原因。状态至少区分 fixed_verified、already_fixed_verified、not_reproduced、deferred、blocked_external、not_run；not_reproduced 不是“已修复”。

只有必需本地实现及必要验证完成、主链路成立且没有未处理的关键正确性/隔离阻塞，才能宣布本轮整体目标完成。未取得官方材料或访问权限时，能完成的代码继续完成，同时保留受影响能力未验证；最终必须分别说明“本轮代码交付完成”和“哪些真实能力仍未验收”，不能用一个“全部完成”覆盖差异。

旧任务中的临时冻结、单次实验数、修正次数、暂停检查点与时间上限，应按原任务上下文解释；新的开发授权不自动恢复旧 job，也不等于永久禁止创建新的隔离任务。永久数据保护规则仍有效。



## 11. 兼容性放宽与按能力准入：本轮新增实施要求

本节依据用户随后明确提出的“避免标准过于死板、拒绝本来能够正确集成的数据”的要求补充。它规定应如何调整准入策略，不表示这些能力已经实现。F01–F40 的历史审查事实保留；第 10 节和配套 Goal Prompt 中“统一门禁”“不得放宽”“不丢行”等概括性表述，须结合本节理解。

**核心要求：每项操作需要与风险相称的证据；一个问题只阻断依赖它的能力。既要阻止错误准入，也要减少对合理输入的错误拒绝。**

### 11.1 统一政策应统一责任与权限，不要求所有能力同时通过

所有入口继续遵守同样的来源身份、不可变输入、当前候选 QA、更新权限和原子发布政策。但保存原始字段、提供事故计数、转换坐标、合并人员表、替换历史数据，所需证据不相同。

实现时复用现有合同、capabilities、blockers 和发布流程，增加必要的适用范围与依赖判断即可。不要为此另建复杂策略平台，也不要把可选能力全部升级为来源接入的前置条件。

- **全局阻塞：**输入/输出完整性失效、宿主执行不可信、隔离失败、目标来源冒用、事务或取消边界无法保证等，继续停止相应任务。
- **操作阻塞：**缺少稳定键、完整覆盖或移除权限，可以阻止增量覆盖/删除；在身份、使用权限和基础数据验证允许的范围内，仍可保留候选或独立版本。
- **能力阻塞：**缺少 CRS、死亡人数定义或辅助表关联时，沿依赖关系禁用相应地图、指标或关系分析；不依赖这些事实的已验证能力可以继续。

保留用户请求的能力、实际达到的能力、未决问题和受影响范围。若用户明确要求的地图仍不可用，不能只发布非空间指标后宣布用户目标全部完成。来源级结果可以表达“已接入，部分能力受限”；具体实现名称沿用现有状态系统，不强制新增另一套枚举。

候选修改为受限范围时，要保留原失败并重新验证适用的合同、输出和依赖；不能把失败检查改成 pass 或直接删去检查。

### 11.2 应放宽的标准与保留的边界

| 原有或容易误解的严格要求 | 本轮应实现的兼容方式 | 仍必须保留的边界 |
|---|---|---|
| 上传必须等于官方端点此刻下载的全部字节 | 精确字节匹配作为快捷证明；支持可验证历史收据/版本、官方发布的哈希/签名、可重放的表示转换或其他已验证资源绑定 | 上传后原文件哈希不变；不同表示有不同原始哈希；仅同表头、相似统计或用户填写 URL 不足以授予官方身份 |
| 只能用某种元数据结构、JSON Pointer 或固定英文措辞 | 允许官方 PDF/HTML、字典、编码表、标准及授权关系组成适用证据链；格式变化交给相应解析/局部调查 | 原文/收据定位、资源/字段/版本作用范围与冲突核查仍必要；模型置信度不代替证据 |
| 所有字段都有完整官方解释才可接入 | 关键字段充分查证；未参与计算/关联的附加列按原值保存，标注语义未解释 | 未解释字段不得参与关键计算、业务键、坐标、覆盖或更新决定 |
| 缺少一项证据或辅助表异常导致整包失败 | 按字段、角色、指标、功能及操作依赖决定最小阻塞范围 | 共享主键、行粒度或基础语义不明时，不得假定其他指标独立正确 |
| 输入与输出永远一行对一行 | 允许有声明、可重放且有独立验证的去重、关联、宽长转换、聚合和隔离处置 | 原始记录保留，每条有去向；不能偷偷丢行、任选重复键、复制父级计数或制造事故记录 |
| 文件中最早/最晚日期必须同时证明完整覆盖 | 分开记录观测时间跨度、声明范围、已证明完整区间与指标可用性 | 观测跨度不能授予补零、删除旧数据或全年完整的资格 |
| 12/24/64 等数量就是永久业务上限 | 按实际字节、展开量、复杂度、内存和墙钟预算组织流式/分块/索引处理，必要数量限制由可信配置控制 | 不删除资源保护，不无限扫描/重试，不由上传内容或模型自行提高预算 |

对来源暂未充分验证、但用户有权处理的数据，可以在项目政策允许时进入明确标注的研究区或候选区；不能冒充已认证官方来源、覆盖同名已验证来源，或晋升为官方可信 recipe。研究区的数据也要执行其适用的质量和隔离检查。

### 11.3 格式等价与来源证明的具体要求

精确匹配官网当前字节是高效证明，但不应是所有合法导入的唯一入口。现有新版本快捷路径的限制不能被当成永久的业务标准。

替代证明应记录方法、适用范围和局限：

- 历史下载收据必须可核验且绑定当时的官方资源与原字节；模型或用户随手构造的 receipt JSON 不等于可信下载收据。
- 使用转换链时保存原始输入、每步规则和输出身份，验证编码、类型、前导零、空值、重复记录数量、日期精度等没有被意外改变。
- 用内容等价证明代替字节相等时，应校验声明范围内完整记录、字段和值；只比行数、总和或少量样本不够。
- 文件名、列顺序、JSON 属性顺序、BOM、换行符或重新打包可能不影响业务含义；是否等价由可验证解析结果决定。
- 表头前的说明行、合理分隔符/编码可以由程序探测并验证；多种解析给出不同业务解释时，仍保留歧义而不能任选。
- 官方迁移/重定向只有在授权与资源身份关系验证后才可兼容；普通外链不授予身份。
- 新增不参与既有计算的备注列可保留为扩展；缺少已声明可选的列可保留对应缺失状态。关键字段删除、改单位、改定义，不能作为普通 schema 宽容处理。

相同字节重传的 0 模型/no_change 目标保留。业务等价但字节不同的输入应能得到相同的适用业务结果；是否 no_change 还取决于有效来源绑定、发布语义身份及更新范围，不承诺所有改写文件都获得同等官方认证。

### 11.4 字段分级、证据形式与能力受限的例子

| 输入情况 | 合理结果 |
|---|---|
| 事故键、日期、粒度已验证，CRS 未确定 | 接入已验证事故属性，保留原坐标但不转换、不用于地图；显式报告 geography 未验证 |
| 有事故分类，没有死亡人数定义 | 按已经验证的分类提供相应指标；死亡人数为 unknown/unsupported，不由 severity 推人数 |
| 事故表有效，车辆表关联有问题 | 基于依赖分析限制车辆分析；只有不依赖问题表的事故指标才可继续 |
| 未使用的官方备注列暂无字典定义 | 原样保存在扩展字段，不要求 Agent 为它无限调查 |
| 只有年度统计 | 保留年度精度并提供年度分析，不生成月份或个体事故 |
| 官方 PDF 定义明确但现有 extractor 不支持 | 优先补适用解析/有定位的结构化主张；不能仅因文档形式判数据无效，也不能跳过语义核对 |
| 原文件仅为有界查询/子集 | 展示实际观测范围与可支持指标；完整覆盖、零月份与旧记录移除仍受限 |

几何能力缺失与几何数据矛盾要分开：前者可以限制地图；后者需要记录冲突及影响。源中 Location 与独立经纬列存在表示舍入差异时，可使用有精度/单位依据的比较规则；容差必须来自已审查的表示或转换精度，不能为某个失败输入临时扩大。

许可状态未知也不能通过填写一句非空文字变成已许可。可否保存、处理或展示按项目已确认的使用权限政策决定；本节不推导某个未知许可资源的法律使用权。

### 11.5 从“输出行数必须不变”改为“原始行去向可追踪”

标准针对输入逻辑记录而非文件物理行数；CSV 引号换行、表头和 Excel 标题区不能混为数据记录。

每条输入记录应能追溯到保留输出、重复组、已声明转换关系、经批准的选择范围或隔离区。不要求宽转长/聚合后的输出行数等于输入行数，但要求使用与操作相匹配的守恒、基数、唯一性和计数分配检查。

- **去重：**先界定完全重复与同键冲突。完全重复可按已验证的去重规则保留代表记录及成员溯源；同键不同值不得任意 first/last。
- **宽长转换或聚合：**声明键、维度、统计粒度、可加性与输出关系，提供独立 expected；不得把汇总人数拆成伪造个体。
- **关联：**检查父键唯一性、匹配/未匹配及 join 基数，防止无意放大事故或伤亡计数。
- **坏行隔离：**原记录、原因和影响保留；根据错误性质及受影响指标判断是否允许受限接入，不采用“坏行低于 1% 就忽略”的通用规则。
- **不可安全恢复的结构错误：**如果解析器无法确定后续记录边界，停止该资源；不能按物理换行猜测跳过。
- **插补：**未经依据不得填值；即使使用有声明的统计估计，也应保存为独立衍生/估计字段，不覆盖原事实或伪装成官方观测。
- **状态与统计：**展示输入、保留、重复/隔离记录及受影响能力；不能把部分记录的结果标成全量官方总数，或者默认补齐其覆盖。

这些放宽需要通用转换算子及相应验证器支撑。开发窗口应实现代表性验收实际需要的能力，不要求一轮支持任意 ETL；尚未实现的操作准确标 unsupported，不能直接删除现有拒绝代码放行任意 Python 输出。

### 11.6 时间覆盖、独立版本与更新权限分开

至少在语义上区分：

- 文件实际观测到的最早/最晚日期；
- 来源/下载查询声明的范围；
- 已证明没有缺口的完整区间；
- 各指标/关系的已验证范围。

没有完整性证明仍可以读取、转换、保存并展示实际记录；前提是其基础身份和语义可用于相应操作。不能因此补零、推导不存在的记录或删除既有数据。

没有跨版本稳定键时，可保留独立候选或不可变版本供分析；不能静默 upsert 到既有来源。snapshot/partition/incremental 的授权依实际影响决定，只有需要移除记录的更新才检查对应移除权限，不应把全量删除证明作为所有只读分析的前置条件。

### 11.8 不变的底线与实施交接

仍不得编造事实、静默丢行/填零、绕过来源更新权限、让生成代码修改自己的 QA、跳过当前候选验证，或在取消/失败后发布不完整事务。文件完整性、宿主故障和权限失败不能降级成普通 warning。

本节授权的是有依据、可追踪、经正反例验证的兼容策略调整。修复时可以修改过度严格的检查和相应测试预期，但必须说明旧规则为何误拒、替代检查如何保障相同风险，并保留安全反例；不能以“所有旧拒绝都必须原样保留”为理由不实施，也不能靠删除断言刷通过。

交接中增加每项放宽的旧规则、适用范围、替代验证、正例/反例与剩余限制，集中放在现有处置表/能力矩阵中即可。原报告的高优先级发布和隔离修复继续推进；本节不授权操作当前业务数据库或历史任务。
